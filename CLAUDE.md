# Cytonn Weekly Draft Generator

AI tool that drafts the first version of the weekly Cytonn Weekly report by pulling data from public sources (and, later, emails and workbooks), mapping it into the report's existing format, checking every figure, and handing a coordinator a ready-to-review draft instead of a blank page. Intern capstone project (Clive Mutende, Vunoh Global AI Intern Program), Option C ("full capstone") scope.

## Status (as of 2026-10-09)

Proposal presented to Cytonn; verbal go-ahead to build, official written approval still outstanding. Digital Payments was the committed pilot and is built end to end up to email delivery of the Word summary; CMS publish (Playwright) is not started. Since 2026-10-05 the tool also knows the other reports that go out in the Weekly slot (quarterly, half-year and annual Markets Reviews, and companion research reports); see **Report types** below. Since 2026-10-09 the weekly report is built end to end on this machine: a coordinator uploads the week's input files, drafts all six sections in the real issue's order, reviews and approves each, and exports the approved report as one Word file (see **The weekly report's inputs**). The six weekly sections, in the order of #38.2026:

| Section | How it is made | What is still missing |
| --- | --- | --- |
| Company Updates | The coordinator's pasted text, carried verbatim (`weekly/company_updates.py`) | Nothing |
| Fixed Income | Worked out from the CBK Weekly Bulletin, CBK's auction results and daily rates, and the fixed income workbook; up to 2 cited highlights; closing outlook carried forward (`fixed_income/weekly.py`) | The analysts' bidding range (typed in, never proposed); confirmations listed under Open items |
| Equities | Worked out from KCB IB's reports, the NSE daily price list (OCR), CBK rates and the equities workbook; up to 3 cited highlights; outlook carried forward (`equities/weekly.py`) | Confirmations listed under Open items |
| Real Estate | Up to 4 rotating themed subsections, NSE Ibuka REITs table | CBK mortgage stats; KBA house price index |
| Digital Payments | Yahoo Finance stock table, 4 IR-first highlights, outlook, exact-match checker, Word summary, email delivery | Highlight citation verification (task 6b, API budget) |
| Focus of the Week | One long-form researched piece on the coordinator's topic | Topic *suggestion* (the original design) is not built |

Every production draft (all narrative drafting in every section) runs on the Anthropic API, and **no production-mode (Anthropic) draft has been run live for any section yet**: that is blocked on API budget approval. The table fetchers, the computed paragraphs of Fixed Income and Equities and the exact-match checker need no LLM, so most of those two sections is the same in dev mode and in production. Digital Payments' chain was live-proven clean on 49 real figures. The other sections' parsers are tested against real source pages and PDFs captured to `backend/tests/fixtures/sources/`.

### Running things (backend/scripts/)

All run from `backend/`; each loads `.env` itself. See also `backend/scripts/README.md`.

```sh
python scripts/check_digital_payments_live.py              # live Yahoo fetch of the DP table; free
python scripts/check_digital_payments_highlights_live.py   # live DP drafting; spends Anthropic budget unless CYTONN_LLM_PROVIDER=local
python scripts/check_exa_ir_sourcing.py                    # what Exa returns per DP highlight company; Exa only, no LLM
python scripts/send_weekly_summary.py                      # PREVIEW the Word-summary email: section, run, approval, drafted_by, recipients, SMTP
python scripts/send_weekly_summary.py --yes                # actually write the .docx and email it to CYTONN_SUMMARY_RECIPIENTS
python -c "from cytonn_weekly.digital_payments.summary import write_latest_summary; print(write_latest_summary())"  # .docx only, no email
```

`send_weekly_summary.py` sends **real email** to Edwin and Liz once real SMTP credentials are in `.env`, so it never sends without `--yes`. It takes an optional section argument (default `digital_payments`), but only sections with a Word summary renderer are accepted, and today that is Digital Payments alone. It exits non-zero, sending nothing, if the latest review is missing, undecided or rejected, if delivery isn't configured, or if any `drafted_by` anywhere in the review starts with `local:`. It checks dev mode itself, even though `delivery.py` checks it again on the send path. It calls `delivery.deliver_latest_summary()`, which reloads the latest review, so after sending it confirms that the run sent is the run it previewed (exit 2 and a warning if a newer run slipped in).

`backend/data/app.db` (gitignored) is created and migrated by `sections.init_db()`, which applies `backend/src/cytonn_weekly/schema.sql`; every `review_store` call does this itself. Secrets and switches live in the gitignored repo-root `.env`; `.env.example` lists every variable the code reads, with what it's for and whether it's required. `create_app()` loads `.env` before reading `CYTONN_WEB_ORIGINS`; the module-level `api.main:app` is built lazily on first access (uvicorn's `getattr`), so importing `create_app` in tests never loads a real `.env`.

No server-side code in `frontend/` calls the API.

Secrets and the provider switches reach the `api` container from the repo-root `.env` through `env_file` only.
- **Ollama:** the local model runs in Ollama on the host. Inside the container "localhost" is the container itself, so the compose file sets `CYTONN_OLLAMA_URL=http://host.docker.internal:11434` (the local provider reads it; unset, it is `http://localhost:11434` as before). On this machine the model runs on the processor only, and running the app in Docker Desktop does not change that.
- **Dev mode is unchanged in Docker:** a draft made with `CYTONN_LLM_PROVIDER=local` is still marked as a development draft (`drafted_by: "local:<model>"`, the DEV MODE ribbon, the NOT FOR CIRCULATION banner, delivery refused).
- **Dev override** (`docker-compose.dev.yml`): mounts `backend/src`, `backend/api` and `backend/scripts` read-only and runs uvicorn with `--reload`; builds the `dev` stage of `frontend/Dockerfile` (`next dev`) with `frontend/src`, `public` and the config files mounted. Both poll for changes, because file events do not cross the Windows mount.
- **Tests in the container:** the `api` container carries the repo-root `.env` (through `env_file`), so `backend/tests/conftest.py` removes the provider switch, the search key, the Ollama address, the CORS and the mail settings from every test's environment (`no_ambient_settings`); a test that needs one sets it itself. The suite gives the same count in the container as natively.
- **`docker compose config` prints the values in `.env`** (it expands `env_file`), secrets included. Use `docker compose config --no-env-resolution` when the output will be shown to anyone.

### Moving the existing database into Docker

The Docker app keeps its database in the `cytonn_data` volume, which starts empty. To start it from the reviews already saved natively, copy `backend/data/app.db` into the volume once, from the repo root:

```sh
docker compose run --rm --no-deps -v "./backend/data:/from:ro" api cp /from/app.db /app/data/app.db
```

It starts a one-off `api` container with `backend/data` mounted read-only at `/from` and copies the file into the volume as the app's own user, so the app can write to it. It overwrites any `app.db` already in the volume.

**Stop both apps first**: the native API (uvicorn) and the Docker one (`docker compose down`). A database copied while either is writing to it can be incomplete.

**After the copy the native app and the Docker app have SEPARATE databases.** A review saved in one is not in the other, and nothing syncs them. `backend/data/app.db` is left as it is.

### Local model speed settings (development only)

Four opt-in environment variables shorten a local (Ollama) draft. They are read in one place, `read_local_settings()` in `digital_payments/providers/local_provider.py`, when a provider is created, and `LocalProvider` and `LocalNarrativeProvider` both use them. The Anthropic provider never reads them. Unset, empty or blank means the default, which is the behaviour before they existed (the requests are pinned by `backend/tests/fixtures/local_provider_requests_before.json`).

| Variable | Range | Default |
| --- | --- | --- |
| `CYTONN_LOCAL_MAX_SEARCH_RESULTS` | 1 to 5 | 5 |
| `CYTONN_LOCAL_RESULT_CHARS` | 500 to 3000 | no extra cut (Exa already returns at most 3000 characters per result) |
| `CYTONN_LOCAL_NUM_THREAD` | 1 to 16 | not sent (Ollama picks the thread count) |
| `CYTONN_LOCAL_NUM_PREDICT` | 1024 to 4096 | 2048 |

- **`num_ctx` is fixed at 8192 and has no variable** (4096 breaks drafts). `keep_alive` is not sent, as before. The `num_predict` minimum is 1024 because a cap of 700 truncates Markets Review briefs. A per-model override in `_MODEL_CONFIG` still wins over `CYTONN_LOCAL_NUM_PREDICT`.
- **An invalid value** (not an integer, or outside the range) logs one warning naming the variable and the range, and the default is used; it is never clamped.
- **Trimming happens after the search, where the prompt is built** (`_trim_results`), so the Exa request and `backend/data/exa_cache/` are the same whatever the settings. The draft is validated against the trimmed list, so a link or claim citing a result the model was not shown is dropped. A result's text is cut at a word boundary and never inside a number; its title and URL are untouched.
- Each provider logs its effective values once, at first use (logger `cytonn_weekly.digital_payments.providers.local_provider`): a WARNING when any setting is off its default, so it shows without any logging setup, and INFO when all four are defaults. Nothing of it enters a draft.
- `docker-compose.yml` forwards the four to the `api` service as `${NAME:-}`, so an unset one arrives empty and is read as unset. The fast preset is in `.env.example`.

## Architecture

Two layers per section, then a single human review:

1. **Drafting layer.** Tables come from public sources via per-section fetchers. Narrative comes from an LLM with web search, written only from what the search returned, every claim carrying its source.
2. **Checking layer.** Before a coordinator sees a draft, every table figure is exact-matched against its normalized source and every claim's figures against its cited text, and every missing part is flagged.

**Process flow:** Draft (each section independently) → Check → Coordinator review (one approve/reject per section) → Word summary to Edwin/Liz (insight only, before publish; Digital Payments only) → Export the approved weekly report as one Word file → Publish (CMS, not built) → Distribute (not built).

### Report types and the section registry: `report_types.py`, `report_sections.py`

A review's key is **(report type, period, section slug)**. `report_types.py` defines the five types (`weekly`, `quarterly`, `half_year`, `annual`, `companion`) and their period labels, stored normalized with a straight apostrophe: `Q3'2026`, `H1'2026`, `FY'2025`, `Weekly #38.2026`. `normalize_period()` refuses what does not fit, with the reason (Q2 is published as the H1 review and Q4 as the annual, so `Q2'2026` is refused); a weekly review may have no label (`""`), every other type needs one. `period_window()` gives the period's first and last day, `year_ago()` the comparison period, `suggested_period()` the period that just ended (the picker's default).

`report_sections.sections_for(report_type, kind=None)` is the ordered section list per type (see **Report types** for what each contains); `spec_for(report_type, slug, kind)` finds one. `SECTIONS`/`BY_SLUG` are the weekly list, in #38.2026's order: Company Updates, Fixed Income, Equities, Real Estate, Digital Payments, Focus of the Week. A weekly period may be an issue label (`Weekly #38.2026`), nothing, or the Friday the week ends on (`Week ending 2026-10-02`, normalized from `2026-10-02`; a day that is not a Friday is refused): that is the label the weekly inputs are filed under, so one week's sections share one period. `DraftContext.week_ending` carries the Friday to the Fixed Income, Equities and Company Updates builders; with no week named they take the latest Friday. With a week named, Real Estate, Digital Payments and Focus are given that Friday as their `today`, so they search and fetch for that week (Digital Payments' forward P/E is still Yahoo's current consensus, which has no history). Each is a `SectionSpec` holding:

- `slug`, `title`, `available`. If not available, it also holds `reason` (what blocks it), `unblock` (what would unblock it), and `built_parts` (what already exists).
- `needs_topic` (Focus: the coordinator supplies the topic), `needs_text` (Company Updates: the coordinator pastes the text), `requires_approved` (Executive Summary: composed only from approved sections).
- `steps`, the run's steps as shown on the start screen; `subsections` and `charts`, the real issue's own headings and chart titles for that section.
- `build(ctx: DraftContext) -> CoordinatorReview`, which lazily imports and calls the section's builder. `DraftContext` carries the report type, period, topic, text and `db_path`. Markets Review builds go through `_periodic()`, which makes a `periodic.common.PeriodContext` and looks the builder up on its module at call time (tests monkeypatch it there).

`latest_runs(db_path, report_type, period)` gives each section's newest run *of that report and period* (the defaults, weekly and `""`, are exactly the pre-report-type runs); `is_this_week()` treats anything from the last 7 days as this week's; `is_current()` is what the screen resumes (an unlabelled weekly run while it is this week's, any labelled run always); `section_slug(review)` returns `review.section["section"]`, or `"digital_payments"` for DP content, which predates the slug field. To add or unblock a section, change its `SectionSpec` (and its builder); the API and the screens read everything from here. `sections.py` is the older section config + permission-flag table in SQLite (seeded with the 5 sections). It is separate from the registry, and the names differ: `sections.name` is "Digital Payments" while the registry and `coordinator_reviews.section` use the slug.

### Two content shapes, one review model

Every section produces a `CoordinatorReview` (`digital_payments/coordinator_review.py`, section-agnostic despite its path) persisted by `digital_payments/review_store.py` under the section's slug, with its `report_type` and `period` (fields on the review, columns in `coordinator_reviews`, fixed at the first save; the API stamps them on every draft). The columns were added by `sections._migrate()`, which `init_db()` runs after `schema.sql`: `ADD COLUMN` with defaults, so every older row reads back as a weekly review with no label, unchanged (tested on an old-schema database and on a byte copy of the real `backend/data/app.db`, whose hash is checked unchanged). A fresh table and a migrated one have identical columns.

- **Digital Payments** has its own pipeline and content shape:
  `fetcher.fetch_digital_payments()` (raw rows) → `highlights.draft_highlights()` / `draft_outlook()` (via a provider) → `compose_section()` → `checkers.digital_payments.check_digital_payments()` → `coordinator_review.build_coordinator_review()`. `digital_payments/review_run.build_digital_payments_review()` wires these and is the only place that does. Content: `items` (highlights), raw table rows, `outlook` with `stats`.
- **Every other section** (including the Markets Reviews' Digital Payments, which is block-shaped so its period columns never touch the weekly table the Word summary reads) uses generic **blocks** (`common/review.py`): `table` (columns with `fmt`/`decimals`, display `rows` stored *beside* raw `source_rows`, `source`), `narrative` (a drafted piece with claims, links, `drafted_by`), `unavailable` (a real report part the tool can't draft yet, with `reason` and `unblock`), and `supplied` (text the coordinator pasted, carried verbatim; one `supplied_text` review item, never verified). The serializer picks the shape by `"blocks" in content`, not by slug. `common/checks.py` exact-matches every numeric table cell using DP's own `check_figure` (same mismatch / missing / sources-disagree semantics; `check_table_block` takes an optional `extra_sources` mapping, `{(row subject, column key): [SourceValue]}`, and hands each list to `check_figure` unchanged, but no caller passes it because no second source exists yet), checks each claim's figures against its cited span, and turns each `unavailable` block into a flag. `common/review.build_review()` makes one `ReviewItem` per table row, claim, and unavailable part, so a coordinator can't approve a section without explicitly acknowledging what's missing. Each section's `review_run.py` (equities, real_estate, focus) runs fetch → draft → compose → `check_section` → `build_review`.
- **Computed paragraphs and the checking policy** (`common/computed.py`, used by the weekly Fixed Income and Equities). Two more block kinds: `computed` (a paragraph of fixed wording around figures the tool worked out; each figure is stored with its `inputs`, each input's `origin` and `source`, and the `expr` that makes it) and `carried` (text copied from the previous issue). `check_figure_record` works every figure out again from its inputs with exact decimal arithmetic, rounds half up to the display precision and requires the printed figure to equal it and to appear in the paragraph. One review item per figure. The policy, applied everywhere:
  - **Computed figures carry their source rows and are exact-matched** (clean when made only of published inputs).
  - **A figure read from a typed workbook cell is shown as "analyst input from <workbook> <sheet>!<cell>" and is not auto-verified, never clean**; so is anything worked out from one. A published source that agrees with a typed cell verifies it; one that differs is a "sources disagree" flag.
  - **An OCR'd figure must agree with a second source.** Confirmed by a published one (KCB's report, afx's own week and year changes while afx's page is still that Friday's) it is clean; agreed only by the analysts' typed value it is not auto-verified; alone, or disagreeing, it is flagged.
  - **Text carried forward from the previous issue is always flagged "carried forward, edit before approving".**
  - A table block can say the same about its rows: `row_origin: "analyst_input"` (or `_origin` on one source row) makes a row that passes its exact-match not auto-verified; `second_sources` are handed to the table check; a column with an `expr`, and a row's `_derived` cells, are worked out again from the row's own raw fields.
  - Builders must compute derived figures with `computed.evaluate` (decimal), never float arithmetic: 399.0 against 400.0 is exactly -0.25%, which rounds half up to (0.3%), and a float gives -0.2499... (the checker caught this on the real Universe of Coverage).
- **Narrative drafting outside DP** goes through `narrative/`: `NarrativeProvider` is DP's provider contract with a *brief* (theme + preferred domains) in place of a company, and it returns DP's `HighlightResult` unchanged. `narrative/drafter.draft_pieces()` tries briefs in priority order up to a target and reports a shortfall rather than backfilling; its `window=(start, end)` replaces the report week (the Markets Reviews pass the period). A brief's `report` and `window` fields name the report and the search window in the prompt; their defaults (`"weekly"`, `"report week"`) keep the weekly prompts word for word (tested). `periodic.common.period_brief()` builds a period brief with no forced opener, since the reviews open their subsections variously. `narrative/factory.get_narrative_provider()` honours the same `CYTONN_LLM_PROVIDER` switch and DEV MODE banner as DP's `provider_factory`.
- **Shared formatting:** `common/formatting.py` (`fmt_value`, `format_rows`, `round_half_up`, `clean_pdf_number`) is the one place display strings are made outside DP. Each table column declares `fmt` (`text`/`number`/`price`/`pct`/`multiple`) and `decimals`, and the checker reads the same column definition, so display precision and check precision can't drift. `common/http.py` is the injectable `get` every fetcher defaults to.

Things that bite if you don't know them:

- **DP's `compose_section()` holds raw fetcher rows, not display strings.** Anything user-facing for DP must call `fetcher.format_table_rows()` first. The DP Average row is not a stored row; it comes from `outlook["stats"]`. (Block-shaped sections store display rows, so they don't have this trap.)
- **`CheckReport` records only flags and a count of figures compared, never what passed.** "Clean" items are everything no flag points at, so a skipped scope would read as all-clean (see Open items).
- **`ReviewItem.status` vs `resolution`:** status is the machine's view (`flagged`/`clean`/`not_auto_verified`); resolution is the coordinator's (`accept`/`fix_needed`). `decide("approved")` needs `is_approvable` (everything resolved, nothing `fix_needed`); `"rejected"` is always allowed; a decision is made once. There's no way to edit a drafted value in review, so approved means "accepted as drafted". A claim that passes the figures-in-cited-span check is still `not_auto_verified`, because its wording is never verified.
- **A decided review is frozen:** `save_review()` raises `ReviewAlreadyDecided` if a stale copy tries to change it. Saves are insert-then-update on `run_id`.
- **`load_latest_review()` returns the newest review whether or not it is decided**; consumers check `.decision`. `write_latest_summary()` and the send script deliberately use the latest, not the latest approved, so a newer unapproved draft blocks summarizing an older week. It takes `report_type` (default **weekly**) and `period` (default `None`, any period of that type), so the weekly Word summary and delivery can never pick up a newer quarterly Digital Payments review (tested).
- **The Word summary and email delivery are Digital-Payments-shaped.** `summary.py`, `delivery.is_dev_mode_review()` and the email subject all read DP content (`items`, `outlook`, the stock table). There's no summary for block-shaped sections yet; `send_weekly_summary.py` only accepts slugs in its `SUMMARY_SECTIONS`. They are also weekly-only by an explicit guard: `summary.require_approved` first calls `require_weekly`, so `write_summary`, `write_latest_summary`, `email_summary` and `deliver_latest_summary` refuse any non-weekly review with `SummaryNotAllowed` (the two `*_latest` functions take `report_type`, default weekly), before any file is written or SMTP is touched (`backend/tests/test_summary_report_type_guard.py`).
- **Dev mode:** library code reads `os.environ` only; entrypoints call `env.load_env()`. With `CYTONN_LLM_PROVIDER=local`, every narrative piece carries `drafted_by: "local:<model>"`, the screen shows a DEV MODE ribbon, the Word doc carries a NOT FOR CIRCULATION banner, and delivery refuses to send. Any new path that could reach a real recipient must check `drafted_by` itself rather than assume an existing guard covers it.

### Review API (`backend/api/`) and screen (`frontend/`)

`backend/api/main.py` (FastAPI) is stateless. Each write loads the review fresh from `review_store`, mutates it with the `CoordinatorReview` methods, saves, and returns the whole review shaped by `backend/api/serialize.py`. Routes:

- `GET /api/sections?report_type=&period=&kind=`: the overview of one report (no arguments: the weekly report with no label, exactly as before). It normalizes the period (422 with the reason if it does not fit) and returns `report` (type, title, normalized period, kind), `report_types` (with `period_hint`, `period_required`, `suggested_period`, `published_as`), `companion_kinds`, and per section: availability, reason/unblock/built_parts, steps, `needs_topic`/`needs_text`/`requires_approved`/`uses_provider`, `subsections`, `charts`, and its latest run *of that report and period* (`this_week`, `current`, decision, progress, per-status counts, dev flag, week, topic). Top-level `drafting` is the draft running right now (slug, title, `report_type`, `period`, `started_at`, `elapsed_seconds`, `stale`), or null. `GET /api/report-types` returns the types and kinds alone.
- `POST /api/sections/{slug}/draft` with `{topic, text, report_type, period, kind}` (all optional; default weekly, no label): runs that section's real pipeline for that report and saves the result. 404 for a slug not in that type, 409 for an unavailable section, 422 for a bad period or a missing Focus topic or Company Updates text, 409 (naming each section and its state) for an Executive Summary whose sections are not all approved. Company Updates and the Executive Summary call no provider: they need no API key and take no draft slot. `POST /api/reviews/draft` is the original DP-only weekly equivalent.
- `POST /api/runs` with `{section, report_type, period, kind, topic, text, provider?}` (202, `{run_id}`): the same draft as the route above, started in a worker thread and answered at once. It goes through the same validation (`resolve_draft()`, shared by both routes), so it refuses the same things in the same words (404, 409, 422, the Q2 and Q4 period refusals, the missing-key 409), and it takes the same draft slot. `provider` is optional and only a check: the provider the screen said a draft would use; a mismatch with `CYTONN_LLM_PROVIDER` is a 409, and it never selects the provider. 409 too if that section of that report and period is already running. A failure once the draft is under way (a source down, Executive Summary sections not yet approved) is the run's `run_failed` event, not an HTTP error. `GET /api/runs/{run_id}` returns the run (`status` running/finished/failed, `events`, `review_id`, `is_dev_draft` and `dev_mode_label` exactly as `backend/api/serialize.py` computes them for the saved review, null until it exists); 404 for an unknown run. `GET /api/runs/{run_id}/events` is a Server-Sent Events stream: every event so far, then each new one, as `event: step` with the event as JSON in `data:`, a `: keepalive` comment every 15 seconds, closing after `run_finished` or `run_failed`. See **Draft runs and run events**.
- `GET /api/reviews/{run_id}`, `GET /api/reviews/latest`, `PATCH /api/reviews/{run_id}/items/{index}`, `POST .../accept-clean`, `POST .../decide`, `GET /api/config` (provider, dev mode, whether a draft spends API budget, and `provider_problem`: why a draft can't run, e.g. anthropic mode with no `ANTHROPIC_API_KEY`; both draft routes refuse such a draft with 409 before taking the slot or fetching anything), `GET /api/health`.
- `GET /api/inputs/weekly/{week_ending}` (what has been received for the week), `PUT .../{slot}?filename=` (upload: the file is the request body; 413 over the size limit, 422 with the reason if it is not the slot's document), `DELETE .../{stored_name}`, `POST .../cbk_bulletin/fetch` (404 if CBK has not published that Friday's issue), `PUT .../notes` (the bidding range, the previous issue). `{week_ending}` must be a Friday (422 otherwise). See **The weekly report's inputs**.
- `GET /api/export/weekly?period=` (each weekly section's state, `ready`, the dev mark) and `POST /api/export/weekly?period=` (the `.docx`; 409 naming each section unless all are approved).

The API, not `review_store`, refuses edits to a decided review. Writes share one lock. **Only one draft runs at a time across every section of every report**: `backend/api/draft_slot.DraftSlot`, one per `create_app()`, in process memory. It records which section holds it and since when, which the overview shows, and the 409 names the holder. A crash releases it (the release is in the route, including on `BaseException`), and so does a restart, because the slot isn't persisted. A *hang* would not release it: each call has only a per-read timeout and no overall deadline. So a claim older than `DRAFT_STALE_AFTER_SECONDS` (1 hour) is treated as stuck, and the next draft takes the slot over. Python can't kill the stuck thread; if it finishes later, `release()` returns False and its result is **discarded, not saved**, so an abandoned run never lands over its replacement. A draft is otherwise saved server-side as soon as it finishes, so a dropped connection never loses a paid run. The API has no authentication.

### Draft runs and run events (`common/run_events.py`, `backend/api/runs.py`)

Every draft builder (each section's `build_*_review`, plus `draft_highlights`, `draft_outlook`, `draft_pieces`, `check_digital_payments` and `check_section`) takes an optional `on_event` observer, default None. With None a builder does exactly what it did before (tested per builder: same review with no argument, with None, with a recording observer and with an observer that raises). An observer is called as `on_event(kind, label, detail=None, counts=None)` and only ever through `run_events.emit()`, which swallows and logs whatever it raises, so an observer can never break a draft. `DraftContext.on_event` carries it through the registry, which passes it to a builder only when it is set (tests monkeypatch builders with fakes that take no such argument).

`RunEvent` has `seq` (from 1), `kind`, `label`, `detail`, `counts` (`clean`, `flagged`, `not_auto_verified`: the review model's own statuses) and `at` (UTC ISO). The only kinds: `run_started`, `source_started`, `source_finished`, `source_failed`, `piece_started`, `piece_finished`, `part_skipped`, `check_started`, `check_finished`, `run_finished`, `run_failed`. What emits what:

- `run_started`, `run_finished`, `run_failed` come from the API's worker (`work_run` in `backend/api/main.py`), never from a builder: a run is finished only once its review is saved. `run_finished` carries the saved review's items per status; `run_failed` carries the error as one line (`failure_message()`: no traceback, and any configured secret an error quotes is redacted).
- `source_*`: one fetch a builder makes (`run_events.fetch_source`): Yahoo Finance, afx.kwayisi.org, the Ibuka summary, each period's CBK T-bond results, KNBS's CPI release, each company's Yahoo price history in the Markets Reviews. A failure a fetcher isolates to one row (a share page, one CBK PDF, one ticker) is a `source_failed` of its own and the draft goes on; a fetch that raises is `source_failed` and then, as before, the builder's error (so `run_failed`).
- `piece_*`: one drafted piece or one table. A headline is not known until the piece is drafted and the two events must share a label, so a narrative piece is labelled with its brief's label or its company (the piece's stored `topic`) and `piece_finished` carries the headline in `detail`. A table only ever finishes (it is built in one step from rows already fetched).
- `part_skipped`: each `unavailable` block, with the stub's blocked reason in `detail`. It also closes the `piece_started` of a theme or company whose search found nothing to draft (`detail` says so), because no other kind says "started, and nothing was drafted".
- `check_*`: one table's exact-match check or one piece's claims. `check_finished` counts are the review items that check produces, so over a run they add up to the review's own counts once the `unavailable` parts (one flagged item each) and supplied text (one unverified item) are added (tested for every builder).
- Nothing else. The Executive Summary and Company Updates have no step of their own (composed or carried in one step), so a run of either is `run_started` then `run_finished` (or `run_failed`).

`backend/api/runs.py` holds the runs: a dict guarded by a lock, **in process memory only**. A restart loses every run, running or finished (its id is then a 404); the review a finished run saved is in the database either way. At most 50 ended runs are kept. **One run per (report type, period, section) at a time**, and the one-draft-at-a-time slot still applies on top to every section that calls a provider. A run that held the slot past the stale limit and was replaced ends `run_failed` and saves nothing, as on the draft route.

**The run view shows only real events.** No simulated progress, no timers, no minimum display times, no invented steps: every line on `/runs/{run_id}` is one event from the list above, worded by the fixed templates in `frontend/src/lib/run.ts`. If nothing is happening, nothing on that screen moves. Keep it so when adding steps: emit where the pipeline really does the thing, never in the screen.

## Non-negotiable rules

- **Nothing in any output is invented or recalled from memory.** Every figure and claim traces to a specific source.
- **Formatting conventions are verified against the real, current report, never assumed.** Check the newest Cytonn Weekly before writing or changing any display format, and cite the line you checked in a comment. The issue's sections are available as JSON (HTML bodies) from `https://cytonnreport.com/api/series/1/research-reports/<id>`; ids are sequential, and #38.2026 (published 2026-09-27) is id 891. Confirmed conventions so far: 1 dp for prices, index levels, percentages and multiples; no currency symbol, no `+`; parentheses for negatives (`(1.9%)`); comma thousands separators (`3,035.6`); KES/USD bn amounts to 1 dp.
- **Checking is exact-match after normalization, not a tolerance band.** Normalize the source to the draft's display precision and units (a mechanical transformation), then require exact equality. **Rounding is round-half-up (`common.formatting.round_half_up`), never Python's `round()`**, which is half-to-even (`round(2.25, 1)` → `2.2`). Real data hits this: Ibuka's 29.65 prints as 29.7 in the report.
- **A mismatch and a source disagreement are different flags.** A draft that doesn't equal its own normalized source is a mismatch. Two legitimate sources giving different derived numbers is "sources disagree": a human call, not a draft error.
- **Only figures that trace to a source are checked, never analysis or opinion.** Check the figure; leave interpretive language unchecked rather than marking it verified.
- **A section's own numeric callouts are checked by table exact-match** (DP's outlook `stats` against its own table), not citation verification.
- **There are no "departments," only report sections.** Analysts rotate weekly; permissions and config are section-based.
- **The tool never approves anything.** One coordinator reviews every section; Edwin and Liz (CEO and co) get the Word summary for awareness before publish, not to sign off.
- **A dev-mode draft (`drafted_by` starting `local:`) never reaches a real recipient,** enforced explicitly on every path that could send or publish.
- **A genuine blocker gets a documented stub**: `NotImplementedError` with a named reason plus an `UNBLOCK` constant, surfaced to the coordinator as an `unavailable` block. Never write a guessed-at implementation. The stubs below stay stubbed until real samples or access arrive.
- **The run view shows only what the pipeline really did.** Every line is a real run event (`common/run_events.py`); no simulated progress, fake delays or invented steps, in the API or the screen.
- **No authentication exists, and nothing may pretend otherwise.** Sign-in with Cytonn SSO is a stub (`backend/api/sso.py`); how Cytonn's sign-in works is never guessed.
- **Publishing is SSO-driven browser automation (Playwright), not a direct API/DB write.** No API or database access has been granted by Cytonn's team (CT). The final report is a PDF that Cytonn's CMS splits into sections: that format was stated by Clive and is not yet confirmed in writing by Cytonn. The publish step is a stub (`backend/api/cms_publish.py`, see Blocked stubs) that nothing in the app can reach.
- **Git is allowed only through the "Publishing to GitHub" procedure below and its allow-list;** every other git use is forbidden. **Commits and PRs carry no AI attribution**: no "Co-Authored-By: Claude", no "Generated with Claude Code", no session links. Commits read as authored by Clive alone.

## Publishing to GitHub

The standing procedure for committing and pushing finished work. The **expected identity** is the single author name and email of the commits already on `origin` (Clive Misiko and his GitHub noreply address), which is also what `git config user.name` and `git config user.email` return. Two local hooks in `.git/hooks/` (not tracked, so a fresh clone does not have them) back the procedure: `commit-msg` refuses an empty message, an attribution trailer or a tool footer; `pre-push` refuses a push to main or master, a deletion, a push that is not a fast-forward, and any commit whose author, committer or message breaks the rules. The hooks are a backstop, not a replacement for the gates below.

### B1. When to publish

At the end of every task that changed tracked files and whose own checks passed, publish the work of that task. Skip publishing if the task prompt contains the words NO PUBLISH, if the task was read-only, or if any gate in B3 fails (then stop and report why; do not publish part of a task).

### B2. Allowed git commands (nothing else)

`status`, `diff`, `log`, `show`, `rev-parse`, `rev-list`, `merge-base`, `ls-files`, `check-ignore`, `branch` (list or show-current only), `fetch origin`, `config --get`, `add <explicit file paths>`, `restore --staged <explicit file paths>`, `commit -F <file>`, `push origin <current branch>` (with `-u` only for a branch's first push), `switch -c <new branch>` (only under B4).

Forbidden: `git add -A`, `git add .`, `git add -p` or any interactive form; `reset`, `rebase`, `merge`, `cherry-pick`, `stash`, `clean`, `rm`, `tag`, `checkout`, `filter-branch`; `commit --amend`; `--no-verify` and `-n`; `--author`, `--trailer`, `-s` or `--signoff`; `push` with `--force`, `-f`, `--force-with-lease`, `--delete`, `--mirror`, `--tags`, or any refspec starting with `+`; `remote add`, `remote set-url`; any `git config` write; any `gh` command that creates or changes a PR, issue or repo. Do not open pull requests. Clive does that.

### B3. Gates before anything is staged (all must hold)

1. **Identity:** `git config user.name` and `user.email` equal the expected identity, none of the `GIT_AUTHOR_*`, `GIT_COMMITTER_*` or `EMAIL` variables are set to anything else, and the identity does not contain claude or anthropic. Otherwise stop.
2. **Tests:** the tests this task ran passed. If the task ran the full suite, it must be green. If it ran only targeted tests, say so in the publish report; do not start a full run just to publish.
3. **Remote state:** run `git fetch origin`. If `origin/<branch>` exists and has commits that the local branch does not have, stop and report. Never merge or rebase to resolve it.
4. **Line endings:** for each modified tracked file, if `git diff --numstat` shows changes but `git diff --ignore-space-at-eol --numstat` shows none, the file only changed line endings. Do not stage it; report it.
5. **Deny list:** never stage any path that matches `.env` or `.env.*` (except `.env.example`), `*.db`, `*.sqlite`, `*.sqlite3`, anything under `backend/data/`, `screenshots/`, `.claude/`, `node_modules/`, `.next/`, `__pycache__/`, `*.log`, `*.pem`, `*.key`, or timing or scratch files. If a path matches, leave it unstaged and name it in the report.
6. **Secret scan:** scan the diff of the files to be staged (for an untracked file, its full content) for the three kinds of hit below. On a hit stop, and report only the file path, line number and pattern name, never the value.
   - A private key block is always a hit.
   - A key prefix (`sk-ant-`, `ghp_`, `github_pat_`, `xox`, `AKIA`) is a hit only when it is followed by at least 16 characters from letters, digits, underscore and hyphen. A prefix mentioned in prose, in a list of patterns, or followed by a backtick, quote or space is not a hit.
   - An assignment to a name containing PASSWORD, SECRET, TOKEN, API_KEY or SMTP is a hit only when the literal value is at least 12 characters long and contains no spaces. Empty values, placeholders and short test values are not hits.

### B4. Branch

Use the current branch if it is not main or master. If the current branch is main or master, create a new branch with `git switch -c` named `work/<short-topic>` (lowercase, hyphens), and push that. Never push main or master.

### B5. Grouping and commits

- Group the task's changed files into topic commits: backend, frontend, Docker and infrastructure, docs, in dependency order. A test file goes in the commit of the code it tests. Stage whole files only, by explicit path.
- Write each message to a temporary file outside the repo (the session scratchpad), commit with `git commit -F <file>`, then delete the file.
- Message format: subject in the imperative, at most 72 characters, no trailing period, then a blank line and a short plain-language body saying what changed and why. Written as the author would write it. No em dashes, no emoji, no trailers, no mention of the tool that produced it.
- Commit as Clive. Do not pass `--author`. Do not run commit with any flag that skips hooks.

### B6. Push

`git push origin <current branch>` only. If the push is rejected by a hook, auth fails, or the remote refuses, stop and report the exact message (redact credentials). Do not retry with different flags, do not ask for tokens, do not try other credentials, and never bypass a hook. Fix the cause (for example a message that tripped the rule) and try once more only if the fix is inside your own commit text.

### B7. Verify after pushing and report

- `git rev-parse HEAD` equals `git rev-parse origin/<branch>`.
- For every commit pushed: author name and email, committer name and email, and a scan of the full message for trailers. All must be the expected identity and no trailers.
- `git status` shows no remaining changes that belonged to this task.

Publish report, in plain text: branch, each commit (short hash and subject), files per commit, tests run and their result, the identity check result, the push result, and anything left unstaged and why.

### This week's inputs (`weekly/inputs.py`, `/api/inputs/weekly/{week_ending}`, `frontend/.../inputs-panel.tsx`)

The workbooks live on the analysts' machines; each Friday they send them and the coordinator uploads them. The panel has a week-ending Friday picker (choosing another Friday switches the report to `Week ending <date>`) and one slot per input: the equities workbook, the fixed income workbook, KCB IB's daily trading reports Monday to Friday, KCB IB's weekly report, the CBK Weekly Bulletin (a "Fetch from CBK" button, or an upload) and, optionally, the NSE yield curve. Each slot shows received or not, **the date read from the file itself**, and whether that is this week. It also takes the analysts' T-bond bidding range and, optionally, the previous issue's address.

- **Storage:** `<CYTONN_DATA_DIR>/inputs/weekly/<week-ending date>/` (`manifest.json`, `notes.json` beside the files), never inside the repository tree; OCR readings are cached in `<CYTONN_DATA_DIR>/inputs/ocr_cache/`. `.gitignore` ignores `backend/data/` whole and `sample data/`.
- **An upload is the request body itself** (`PUT /api/inputs/weekly/{week}/{slot}?filename=`), so no multipart dependency. It is checked before it is kept: size (30 MB), kind by its first bytes (never its name), and that it parses as the slot's document. A KCB daily report is filed under the date printed in it and refused if that day is outside the week; KCB's weekly report in the daily slot is refused; a workbook for another week is stored and shown as not this week's.
- **Nothing is guessed.** A reader finds its cell by sheet name plus a label or a date, never a fixed row (`weekly/workbook.py`), and says what is missing in the coordinator's terms: "'NASI-PE & Dividend Yield' has no row for 2026-10-09: workbook not yet updated for this week". A missing input is never an error: the part that needed it becomes an `unavailable` block naming it.
- **Confidentiality.** The workbooks, KCB's reports and figures that come only from them (target prices, DPS, EPS, the P/E series, the fund table, bank placements, the turnover series) are never committed, in code, tests or docs.

### Parsers (`weekly/`)

- **`kcb.py`**: KCB IB's daily and weekly trading reports (one-page PDFs with a text layer). **They cover NSE equities only**: no T-bills, money market, Eurobonds or shilling. Read by printed label: the date under the title; the indicators (NASI, NSE-20, NSE-25, market cap, shares, "Equities TO", foreign buy, sell, net) for the two dates in the header row; TRADING STATS' Equities row; each security's price and change; on the weekly report, DAILY FOREIGN FLOWS by weekday. The equities turnover is the **TRADING STATS Equities row**, not the "Equities TO" indicator, which includes ETFs on the weekly report. The text layer kerns digits apart ("1 2,327,385"), so `split_numbers` accepts a row only when there is exactly one way to cut its tokens into the expected count of well-formed numbers (no leading zeros; one indicator's two figures share their decimals), and flows are checked arithmetically to within the report's whole-shilling rounding.
- **`cbk_bulletin.py`**: the CBK Weekly Bulletin, published on a Friday and covering the Friday before to the Thursday before. Table 1 exchange rates; Table 2 reserves and months of import cover; Table 3 interbank deals, value and KESONIA with a weekly average row; Table 4 T-bill auctions (this week's and the previous week's side by side); Table 5 T-bond auctions as printed; Table 6 daily NASI, NSE 25, NSE 20, equity turnover, market cap, bond turnover and Eurobond yields, each yield column matched to the maturity year printed above it by position. **It is fetched by date**: the listing page (`/weekly-bulletin/`) links every issue under `/uploads/weekly_bulletin/` with the issue date in the file name, written several ways.
- **`cbk_rates.py`**: CBK's daily US dollar rate, fetched from the data table behind the Forex page (`admin-ajax.php?action=get_wdtable&table_id=193`, a form POST answering JSON). It is current to the day and holds about two years. The older table on `/rates/forex-exchange-rates/` and the "historical data" CSV both stop in January 2024.
- **`nse_price_list.py`**: the NSE daily equity price list, `https://www.nse.co.ke/wp-content/uploads/DD-MON-YY.pdf`, a scanned image with no text layer. Its index box is the only public source of the **NSE 10 and the Banking Sector index**. **OCR: `rapidocr-onnxruntime`** (pinned in `pyproject.toml`): it installs with pip alone on Windows and in the image, with its models inside the wheel; Tesseract needs a separate program and EasyOCR pulls in PyTorch and downloads models. In Docker its OpenCV dependency needs `libgl1` and `libglib2.0-0`, which `backend/Dockerfile` installs (the image has not been rebuilt and run since). OCR is never trusted alone: a whole-page pass finds the box, the box is cut out and read twice (at the scan's size and enlarged), and a figure is kept only if both readings agree. A reading takes about half a minute and is cached per PDF.
- **`nse_yield_curve.py`**: the NSE yield curve PDF (91 and 182 days, 1 to 29 years), interpolated linearly between whole years and never extrapolated.
- **`equities_workbook.py`**, **`fi_workbook.py`**: the two workbooks (sheet names verbatim, two with a trailing space). What each reads is in its docstring.
- **`previous_issue.py`**: the previous issue on cytonnreport.com. There is no listing endpoint: `/series/1` links the newest issue, `/api/global/search/<text>` resolves a page name to an id, and ids are walked down to the newest issue published on or before the week's Friday. A pasted address or id overrides it.

### Week windows

Equities, turnover and foreign flows: Monday to Friday. The shilling: Friday to Friday. The interbank market: Friday to Thursday (the bulletin's weekly row). Eurobond yields: the last six trading days up to Thursday. T-bills: the week's Thursday auction, whose value date is the following Monday (a workbook is this week's when its value date falls in the seven days after the Friday). The year-to-date base everywhere is the year's first trading day, read from the source (`weekly/week.py`).

### Fixed Income (`fixed_income/weekly.py`)

In the issue's order: T-bills (subscription overall and by tenor against the previous week, acceptance, each tenor's yield and its change in bps: the yield is CBK's weighted average rate of accepted bids; from the bulletin's Table 4, cross-checked with the workbook); T-bonds (the week's primary results from CBK's results PDFs, cross-checked with the bulletin's Table 5) and **the analysts' recommended bidding range, their own text or an empty part, never a range the tool made up** (the NSE curve's yield at each auctioned bond's remaining tenor is shown as context only); Money Market Performance (3-month bank placements, the 91-day and 364-day yields, the Cytonn fund, the Top 5 funds' average, which is **the average of this week's five highest rates in the table**, and the ranked fund table); Liquidity (volumes from the bulletin's Table 3; the rate change from the workbook's daily rates, to two decimals of a basis point); Kenya Eurobonds (the biggest mover and the table: five issues, the 2025 11-year left out; days the bulletin prints come from the bulletin with the workbook as second source, the 2 January and month-start rows from the workbook; Amount Issued and Years to Maturity worked out from the workbook's issue list, to the table's last day; changes in percentage points); Kenya Shilling (Friday to Friday and year to date from CBK's rates; remittances; reserves from the bulletin's Table 2; the pressure bullets carried forward); the weekly highlights (cited narrative, as every section's); the closing outlook carried forward **without its own borrowing sentence**, and the net domestic borrowing sentence worked out: net borrowing over the target pro-rated by days from the fiscal year's start to the latest auction's value date over a 364-day year, worded "is at X% of its pro-rated ... target" and never "ahead".

### Equities (`equities/weekly.py`)

The real weekly prints **no indices table and no gainers or losers table**, so none is printed (afx stays as the OCR cross-check; `equities/review_run.py`'s afx-table builder is no longer in the registry and serves only as a stand-in in older tests). Market Performance: the four indices' week, ordered by the size of the move, and year to date (NASI, NSE 20 and NSE 25 from KCB's weekly report; NSE 10 and the Banking index by OCR for the two Fridays; year opens by OCR of the year's first trading day's list); the large-cap movers (the biggest movers among the workbook's large-cap list, by KCB's week-on-week changes); the Banking index; turnover in USD (each day's KES turnover over that day's CBK rate: KCB's daily report, else the bulletin's Table 6, else the price list by OCR; the bulletin covers Friday to Thursday, so with it only the Friday needs KCB's daily report); foreign investors' net position in USD (KCB's weekly report lists each weekday) with the streak and year-to-date totals from the workbook; the P/E against its average, the dividend yield against its average in percentage points, and the PEG (the P/E over a fixed 8). Then the Universe of Coverage table: w/w against last Friday, m/m against the previous month's last close, YTD against the 2 January close, dividend yield DPS over price, upside dividend yield plus target over price less one, P/TBV price over tangible book per share; recommendation Buy from 20%, Accumulate from 10%, Hold from 5%, Lighten from 0.1%, Sell at or below 0, and **nothing between 0% and 0.1%, which is flagged, not filled**; sorted by upside. Then the highlights and the outlook carried forward.

### Section summaries (`weekly/summaries.py`)

On cytonnreport.com every section has a body and a summary (1,500 to 3,000 characters of its own lead paragraphs), and the website builds the Executive Summary from the summaries. A summary here is composed, never drafted: Fixed Income and Equities compose theirs from their computed lead paragraphs; the drafted sections' is the opening paragraph of each piece, never cut inside a paragraph; Company Updates has none, as published. `serialize_review` returns it as `summary`.
### Export (`weekly/export.py`, `GET`/`POST /api/export/weekly?period=`, `frontend/.../export-bar.tsx`)

"Export weekly report" on the weekly overview writes the approved week as one `.docx` and downloads it. **It is enabled only when every weekly section of that report and period is approved**: the API answers 409 naming each section that is not ("Fixed Income (still in review); Equities (not drafted); ..."), and writes nothing. The file is kept under `<CYTONN_DATA_DIR>/exports/weekly/`.

- The six sections under the issue's own headings and in its order (Company Updates, Fixed Income, Equities, Real Estate, Digital Payments Weekly Highlights, Focus of the Week); every table as a Word table with its source line and footnotes; the Eurobond table as the issue prints it (issues across, the fixed rows on top), built from the checked display strings (`export_grid`).
- Each chart of the real issue as `[Chart to add: <caption>]`, after the part the issue puts it under (`chart_after` in the section content; the tool draws no charts).
- Carried-forward text under a red `[Carried forward from the previous issue: edit before publishing]` line, and a part approved as missing as `[Not included: ...]`, so neither passes for finished copy.
- A final part, "Section summaries for the CMS": each section's summary in the same order.
- **Dev mode:** if any section holds a piece drafted by the local model, the file carries the DEV MODE label at the top of every page and a diagonal watermark behind it, the status says so, and `export.refuse_to_send()` raises `DevModeDeliveryBlocked` (the same test `delivery.py` uses). **Nothing sends or publishes the export**: it is handed to the coordinator who asked for it, and no email or CMS path exists for it. A future one must call `refuse_to_send` itself.
