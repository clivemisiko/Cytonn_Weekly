# Cytonn Weekly Draft Generator

AI tool that drafts the first version of the weekly Cytonn Weekly report by pulling data from public sources (and, later, emails and workbooks), mapping it into the report's existing format, checking every figure, and handing an analyst a ready-to-review draft instead of a blank page. Intern capstone project (Clive Mutende, Vunoh Global AI Intern Program), Option C ("full capstone") scope.

## Status (as of 2026-11-17)

Proposal presented to Cytonn; verbal go-ahead to build, official written approval still outstanding. Digital Payments was the committed pilot and is built end to end up to email delivery of the Word summary; CMS publish (Playwright) is not started. Since 2026-10-05 the tool also knows the other reports that go out in the Weekly slot (quarterly, half-year and annual Markets Reviews, and companion research reports); see **Report types** in backend/src/cytonn_weekly/periodic/CLAUDE.md. Since 2026-10-09 the weekly report is built end to end on this machine: an analyst uploads the week's input files, drafts all five sections in the real issue's order, reviews and approves each, and exports the approved report as one Word file (see **The weekly report's inputs** in backend/src/cytonn_weekly/weekly/CLAUDE.md). The five weekly sections, in the order of #38.2026 (Company Updates is not one of them: the CT team writes it after the exported document is received and before publishing, so the tool does not draft it):

| Section | How it is made | What is still missing |
| --- | --- | --- |
| Fixed Income | Worked out from the CBK Weekly Bulletin, CBK's auction results and daily rates, and the analysts' own figures (typed on the weekly analyst inputs form, or read from the fixed income workbook when it is uploaded); the net domestic borrowing log is built from CBK's result files (`fixed_income/net_borrowing.py`); up to 2 cited highlights; closing outlook carried forward (`fixed_income/weekly.py`) | The analysts' bidding range (typed in, never proposed); confirmations listed under Open items |
| Equities | Worked out from KCB IB's reports, the NSE daily price list (OCR), CBK rates and the analysts' own figures (the form, or the equities workbook when it is uploaded); up to 3 cited highlights; a "Listed banks and insurers" part written from each company's own website (`equities/companies.py`); outlook carried forward (`equities/weekly.py`) | Confirmations listed under Open items; every company's website is set in `equities/companies.json` |
| Real Estate | Four sectors written from the analyst's snips (Industry reports, Residential sector, Land, Hospitality and Tourism), and the NSE Ibuka REITs part | Nothing for the weekly: CBK mortgage stats and the house price index are periodic publications that do not print in the weekly every week (team, 30 Oct), so they are needed only for the quarterly, half-year and annual reviews |
| Digital Payments | Yahoo Finance stock table, 4 IR-first highlights, outlook, exact-match checker, Word summary, email delivery | Highlight citation verification (task 6b, API budget) |
| Focus of the Week | **The tool does not draft Focus text (2026-11-17).** It keeps the outline step and, per section, collects findings only (claim, verified quote and source, no paragraph) as research notes; the contents list and the carried disclaimer stay in the review; the Word export prints "Focus of the Week: analyst to write" and never the findings (`focus/review_run.py`) | Topic *suggestion* (the original design) is not built; the analyst writes the Focus, with Cytonn's own tables, charts and recommendations |

Every production draft (all narrative drafting in every section) runs on Amazon Bedrock (the direct Anthropic provider was removed on 2026-11-16), and **production-mode (Bedrock) drafts have been run live for the investments team**. The table fetchers, the computed paragraphs of Fixed Income and Equities and the exact-match checker need no LLM, so most of those two sections is the same in dev mode and in production. Digital Payments' chain was live-proven clean on 49 real figures. The other sections' parsers are tested against real source pages and PDFs captured to `backend/tests/fixtures/sources/`.

### Running things (backend/scripts/)

All run from `backend/`; each loads `.env` itself. See also `backend/scripts/README.md`.

```sh
python scripts/check_digital_payments_live.py              # live Yahoo fetch of the DP table; free
python scripts/check_digital_payments_highlights_live.py   # live DP drafting; spends Anthropic budget unless CYTONN_LLM_PROVIDER=local
python scripts/check_exa_ir_sourcing.py                    # what Exa returns per DP highlight company; Exa only, no LLM
python scripts/send_weekly_summary.py                      # PREVIEW the Word-summary email: section, run, approval, drafted_by, recipients, SMTP
python scripts/send_weekly_summary.py --yes                # actually write the .docx and email it to CYTONN_SUMMARY_RECIPIENTS
python -c "from cytonn_weekly.digital_payments.summary import write_latest_summary; print(write_latest_summary())"  # .docx only, no email
```

`send_weekly_summary.py` sends **real email** to `CYTONN_SUMMARY_RECIPIENTS` once real SMTP credentials are in `.env`, so it never sends without `--yes`. It takes an optional section argument (default `digital_payments`), but only sections with a Word summary renderer are accepted, and today that is Digital Payments alone. It exits non-zero, sending nothing, if the latest review is missing, undecided or rejected, if delivery isn't configured, or if any `drafted_by` anywhere in the review starts with `local:`. It checks dev mode itself, even though `delivery.py` checks it again on the send path. It calls `delivery.deliver_latest_summary()`, which reloads the latest review, so after sending it confirms that the run sent is the run it previewed (exit 2 and a warning if a newer run slipped in).

`backend/data/app.db` (gitignored) is created and migrated by `sections.init_db()`, which applies `backend/src/cytonn_weekly/schema.sql`; every `review_store` call does this itself. Secrets and switches live in the gitignored repo-root `.env`; `.env.example` lists every variable the code reads, with what it's for and whether it's required. **An environment variable beats `.env`** (`load_env()` uses `override=False`), so a key left in a Windows user variable or the shell is the one used, and editing `.env` changes nothing until that variable is removed. At start the API logs one warning per API key (only `EXA_API_KEY`, and only when `CYTONN_LLM_PROVIDER=local`) that the environment and `.env` both hold with different values, naming each by its last four characters and saying the environment's wins (`env.key_override_warnings()`); no key is ever shown or logged beyond its last four. In local mode a draft is refused up front (409) when `EXA_API_KEY` is missing or empty, as the Bedrock path is without its AWS settings, and a key Exa refuses (401 or 403) ends the run with a plain message naming the key's last four and, when the environment overrides `.env`, saying so (`SearchKeyError` in `drafting/local.py`). `create_app()` loads `.env` before reading `CYTONN_WEB_ORIGINS`; the module-level `api.main:app` is built lazily on first access (uvicorn's `getattr`), so importing `create_app` in tests never loads a real `.env`.

**PostgreSQL (Supabase) and the held connection** (`backend/src/cytonn_weekly/db.py`, the only file that opens a database). With `CYTONN_DATABASE_URL` set and no explicit `db_path`, the app uses PostgreSQL; see `.env.example`. On PostgreSQL one connection is kept for the process and lent to one caller at a time (`_held`, behind `_held_lock`); `Db.close()` gives it back and does not close it. The owner measured against the Supabase pooler (5 samples, median) 1287 ms to open a connection and 211 ms for one trivial query, so before this every store call paid about 1.5 s to connect. Rules: a call waits for the lock at most 60 s, then raises the unreachable error (log word `lock wait`); a connection idle over 30 s is tested with `SELECT 1` before it is used; a **read** that loses the connection is retried once on a new one, a **write**, or a read inside a transaction, is never replayed; every new connection sets libpq keepalives (1, 30 s, 10 s, 3) and `statement_timeout = '30s'`; it is closed at exit and at app shutdown (`db.close_all()`). SQLite is unchanged: each call opens and closes its own. A connection-class error (`db.is_connection_error`) reads "Could not reach the database..."; any other database error reads "The database rejected the request. See the server log." with no detail. The URL travels as `db._SecretUrl`, a `str` whose repr is `'***'` (equality and `str()` are the str's own), so a traceback's argument list never prints the password; a failure that is not a driver error is logged as its class and message with the URL, user and password redacted. All database work in one process is serialised: **if more than one analyst ever works at once, the upgrade is a pool (`psycopg_pool`)**. `backend/tests/test_connection_counts.py` pins how many connections each route opens on SQLite; `test_db_held_connection.py` tests the reuse with a fake driver; `conftest.py` clears the held connection around every test.

- **One copy at a time.** Docker publishes the native ports (8000, 5173), so the native API and `npm run dev` must be stopped first, and the reverse.
- **Services and ports:** `api` (target `runtime` of `backend/Dockerfile`: Python 3.12-slim, `libgl1` and `libglib2.0-0` for the OCR, `pip install -e .` with no test extra, user UID 10001 with a home folder for matplotlib's cache) on `127.0.0.1:8000`; `web` (target `runner` of `frontend/Dockerfile`: the app built with `npm run build` and served by `vite preview` on 3000, published as `127.0.0.1:5173`), started once `api` is healthy. `vite preview` proxies `/api` to `VITE_API_TARGET` (`http://api:8000`, set in `docker-compose.yml`), event stream included; uploads are refused by the API itself at 30 MB. `frontend/nginx.conf` is kept in the repo but no Dockerfile or compose file uses it.
- **The ports stay on 127.0.0.1 until a sign-in exists.** The app has no authentication, so it is never published on 0.0.0.0 or made reachable from another machine.
- **Data:** `./backend/data` is bind-mounted at `/app/data` (`CYTONN_DATA_DIR=/app/data`): the same inputs, charts, exports and search cache as a native run. There is no named volume. Whether the container user can write to the Windows (OneDrive) folder through the mount is not yet proven (step 2).
- **Database:** the same Supabase database as a native run, from `.env` through `env_file` at run time only (never an image, a build argument or a layer). Compose sets `CYTONN_REQUIRE_POSTGRES=1`, so without `CYTONN_DATABASE_URL` `db.target()` raises and `create_app()` refuses to start: the Docker app never creates or opens a SQLite `app.db` in the real data folder (`backend/tests/test_require_postgres.py`; conftest clears the marker like the other settings).
- **Startup logs:** `key_override_warnings()` compares the environment with a `.env` file; the container has no `.env` file (its variables come from `env_file`), so it logs nothing, and no key fragment reaches `docker logs`.
- **Ollama:** the local model runs in Ollama on the host. Inside the container "localhost" is the container itself, so the compose file sets `CYTONN_OLLAMA_URL=http://host.docker.internal:11434` (the local provider reads it; unset, it is `http://localhost:11434` as before). On this machine the model runs on the processor only, and running the app in Docker Desktop does not change that.
- **Dev mode is unchanged in Docker:** a draft made with `CYTONN_LLM_PROVIDER=local` is still marked as a development draft (`drafted_by: "local:<model>"`, the DEV MODE ribbon, the NOT FOR CIRCULATION banner, delivery refused).
- **Dev override** (`docker-compose.dev.yml`, updated 2026-10-23, not yet run): mounts `backend/src`, `backend/api` and `backend/scripts` read-only and runs uvicorn with `--reload`; builds the `dev` stage of `frontend/Dockerfile` (Vite's dev server on 8080, proxying `/api` to `VITE_API_TARGET=http://api:8000`) with `frontend/src`, `public`, `index.html` and the config files mounted. Both poll for changes, because file events do not cross the Windows mount (`VITE_USE_POLLING`, read in `vite.config.ts`).
- **Tests** are not in the runtime image: `docker build --target test -t cytonn-api-test backend`, then `docker run --rm --network none cytonn-api-test` (no `.env`, no data folder, no network; the PostgreSQL smoke tests are deselected).
- **Never run `docker compose config` without `--quiet` or `--no-env-resolution`:** it expands `env_file` and prints the database URL with its password.

### Local model speed settings (development only)

Four opt-in environment variables shorten a local (Ollama) draft. They are read in one place, `read_local_settings()` in `digital_payments/providers/local_provider.py`, when a provider is created, and `LocalProvider` and `LocalNarrativeProvider` both use them. The Anthropic provider never reads them. Unset, empty or blank means the default, which is the behaviour before they existed (the requests are pinned by `backend/tests/fixtures/local_provider_requests_before.json`).

| Variable | Range | Default |
| --- | --- | --- |
| `CYTONN_LOCAL_MAX_SEARCH_RESULTS` | 1 to 5 | 5 |
| `CYTONN_LOCAL_RESULT_CHARS` | 500 to 3000 | no extra cut (Exa already returns at most 3000 characters per result) |
| `CYTONN_LOCAL_NUM_THREAD` | 1 to 16 | not sent (Ollama picks the thread count) |
| `CYTONN_LOCAL_NUM_PREDICT` | 1024 to 4096 | 2048 |

- **`num_ctx` is fixed at 8192 and has no variable** (4096 breaks drafts). `keep_alive` is not sent, as before. The `num_predict` minimum is 1024 because a cap of 700 truncates Markets Review briefs. A per-model override in `_MODEL_CONFIG` still wins over `CYTONN_LOCAL_NUM_PREDICT`.
- **An invalid value** (not an integer, or outside the range) logs one warning naming the variable and the range, and the default is used; it is never clamped.
- **Trimming happens after the search, where the prompt is built** (`_trim_results`), so the Exa request and `backend/data/exa_cache/` are the same whatever the settings. The draft is validated against the trimmed list, so a link or claim citing a result the model was not shown is dropped. A result's text is cut at a word boundary and never inside a number; its title and URL are untouched.
- Each provider logs its effective values once, at first use (logger `cytonn_weekly.digital_payments.providers.local_provider`): a WARNING when any setting is off its default, so it shows without any logging setup, and INFO when all four are defaults. Nothing of it enters a draft.
- `docker-compose.yml` forwards the four to the `api` service as `${NAME:-}`, so an unset one arrives empty and is read as unset. The fast preset is in `.env.example`.

## Architecture

Two layers per section, then a single human review:

1. **Drafting layer.** Tables come from public sources via per-section fetchers. Narrative comes from an LLM with web search, written only from what the search returned, every claim carrying its source.
2. **Checking layer.** Before an analyst sees a draft, every table figure is exact-matched against its normalized source and every claim's figures against its cited text, and every missing part is flagged.

**Process flow:** Draft (each section independently) → Check → Analyst review (one approve/reject per section) → the analyst exports the approved weekly report as one Word file → Coordinator reviews the whole document → Publish (CMS, not built) → Distribute (not built).

### Report types and the section registry: `report_types.py`, `report_sections.py`

A review's key is **(report type, period, section slug)**. `report_types.py` defines the five types (`weekly`, `quarterly`, `half_year`, `annual`, `companion`) and their period labels, stored normalized with a straight apostrophe: `Q3'2026`, `H1'2026`, `FY'2025`, `Weekly #38.2026`. `normalize_period()` refuses what does not fit, with the reason (Q2 is published as the H1 review and Q4 as the annual, so `Q2'2026` is refused); a weekly review may have no label (`""`), every other type needs one. `period_window()` gives the period's first and last day, `year_ago()` the comparison period, `suggested_period()` the period that just ended (the picker's default).

`report_sections.sections_for(report_type, kind=None)` is the ordered section list per type (see **Report types** in backend/src/cytonn_weekly/periodic/CLAUDE.md for what each contains); `spec_for(report_type, slug, kind)` finds one. `SECTIONS`/`BY_SLUG` are the weekly list, in #38.2026's order: Fixed Income, Equities, Real Estate, Digital Payments, Focus of the Week. A weekly period may be an issue label (`Weekly #38.2026`), nothing, or the Friday the week ends on (`Week ending 2026-10-02`, normalized from `2026-10-02`; a day that is not a Friday is refused): that is the label the weekly inputs are filed under, so one week's sections share one period. `DraftContext.week_ending` carries the Friday to the Fixed Income and Equities builders; with no week named they take the latest Friday. With a week named, Real Estate, Digital Payments and Focus are given that Friday as their `today`, so they search and fetch for that week (Digital Payments' forward P/E is still Yahoo's current consensus, which has no history). Each is a `SectionSpec` holding:

- `slug`, `title`, `available`. If not available, it also holds `reason` (what blocks it), `unblock` (what would unblock it), and `built_parts` (what already exists).
- `needs_topic` (Focus: the analyst supplies the topic), `requires_approved` (Executive Summary: composed only from approved sections).
- `steps`, the run's steps as shown on the start screen; `subsections` and `charts`, the real issue's own headings and chart titles for that section.
- `build(ctx: DraftContext) -> CoordinatorReview`, which lazily imports and calls the section's builder. `DraftContext` carries the report type, period, topic, text and `db_path`. Markets Review builds go through `_periodic()`, which makes a `periodic.common.PeriodContext` and looks the builder up on its module at call time (tests monkeypatch it there).

`latest_runs(db_path, report_type, period)` gives each section's newest run *of that report and period* (the defaults, weekly and `""`, are exactly the pre-report-type runs); `is_this_week()` treats anything from the last 7 days as this week's; `is_current()` is what the screen resumes (an unlabelled weekly run while it is this week's, any labelled run always); `section_slug(review)` returns `review.section["section"]`, or `"digital_payments"` for DP content, which predates the slug field. To add or unblock a section, change its `SectionSpec` (and its builder); the API and the screens read everything from here. `sections.py` is the older section config + permission-flag table in SQLite (seeded with the 5 sections). It is separate from the registry, and the names differ: `sections.name` is "Digital Payments" while the registry and `coordinator_reviews.section` use the slug.

## Testing conventions

- `backend/tests/conftest.py` autouse-sets placeholder AWS settings (`AWS_REGION` and `AWS_BEARER_TOKEN_BEDROCK`, and it clears the other AWS variables and `BEDROCK_MODEL_ID`) and `CYTONN_LLM_PROVIDER=bedrock`, so faked-pipeline drafts pass the API's settings check and a real shell value is never seen; it also clears the ambient database, provider, local-model, Exa, web-origin and SMTP settings, so no test can reach a real service. Tests of a missing-settings refusal delete the placeholders themselves. It also autouse-redirects `db._DEFAULT_DB` to a per-test temp file. Anything with `db_path=None` (including the review API) would otherwise write to the real `backend/data/app.db`; this has happened once, so don't remove the guard.
- **Tests may run in parallel by file (`-n auto --dist loadfile`): a test must use only `tmp_path` and `monkeypatch` for anything it writes or changes.** Module-scoped fixtures (`test_weekly_export.py`, `test_weekly_inputs.py`) and the OCR engine are per worker, and `loadfile` keeps each file on one worker. Checked 2026-10-23: no fixed port, no shared file under `backend/data`, no unmonkeypatched `os.environ` write, and no locale-dependent date format (`day_text()` and the other `%b`, `%B`, `%A` uses write English month and day names; no code calls `setlocale`).
- **No test reaches the network, from any thread, for the whole session.** `conftest._block_network()` refuses every non-loopback socket connection and DNS lookup when conftest is imported, and is never undone. A per-test patch is not enough: a run started with `POST /api/runs` keeps working in its own thread after the test ends (on 2026-10-09 such a thread reached the Anthropic API with the placeholder key and was refused). The weekly inputs default to a per-test temp folder (`inputs._DEFAULT_ROOT`), like the database.
- **Weekly inputs in tests are synthetic.** `backend/tests/weekly_helpers.py` builds workbooks with the real sheet names and layout and invented figures, and KCB report text as its text layer reads (`fake_pdf` plus the `text_pdfs` fixture stand in for a PDF). The real workbooks and KCB reports are confidential and never in the repository; `sample(name)` gives them to the few golden tests that need them and **skips** when they are absent or locked (`CYTONN_SAMPLE_DIR` names another folder than `sample data/`). Public documents are fixtures: the CBK Weekly Bulletins of 2 October 2026 and 9 October 2026 (two page layouts; both whole files, byte for byte as CBK serves them), the NSE daily price list of 8 October 2026 (the OCR golden), the NSE yield curve, and CBK's rates and T-bond results for the golden week. Run pytest with `--tb=short`: a long traceback prints local variables, which once included the process environment.
- `backend/tests/review_helpers.py` builds real DP `CoordinatorReview`s by running the real draft/compose/check code on a fake provider and fixed price rows (`make_review(tamper=True)` plants a mismatch and a missing row; `LocalFakeProvider` makes a dev-mode draft). `backend/tests/section_helpers.py` does the same for Equities, Real Estate and Focus, using a `FakeNarrativeProvider` and figures from the real captured sources. `backend/tests/periodic_helpers.py` does it for every Markets Review section (`BUILDERS`, `ctx()`, a CBK getter serving the captured PDFs by value date); it binds the real builders at import, so a test that monkeypatches a periodic module's builder (to fake an API draft) still gets the real pipeline from the helpers. Prefer all three over hand-built dicts.

## Non-negotiable rules

- **Nothing in any output is invented or recalled from memory.** Every figure and claim traces to a specific source.
- **Formatting conventions are verified against the real, current report, never assumed.** Check the newest Cytonn Weekly before writing or changing any display format, and cite the line you checked in a comment. The issue's sections are available as JSON (HTML bodies) from `https://cytonnreport.com/api/series/1/research-reports/<id>`; ids are sequential, and #38.2026 (published 2026-09-27) is id 891. Confirmed conventions so far: 1 dp for prices, index levels, percentages and multiples; no currency symbol, no `+`; parentheses for negatives (`(1.9%)`); comma thousands separators (`3,035.6`); KES/USD bn amounts to 1 dp.
- **Checking is exact-match after normalization, not a tolerance band.** Normalize the source to the draft's display precision and units (a mechanical transformation), then require exact equality. **Rounding is round-half-up (`common.formatting.round_half_up`), never Python's `round()`**, which is half-to-even (`round(2.25, 1)` → `2.2`). Real data hits this: Ibuka's 29.65 prints as 29.7 in the report.
- **A mismatch and a source disagreement are different flags.** A draft that doesn't equal its own normalized source is a mismatch. Two legitimate sources giving different derived numbers is "sources disagree": a human call, not a draft error.
- **Only figures that trace to a source are checked, never analysis or opinion.** Check the figure; leave interpretive language unchecked rather than marking it verified.
- **A section's own numeric callouts are checked by table exact-match** (DP's outlook `stats` against its own table), not citation verification.
- **There are no "departments," only report sections.** Analysts rotate weekly; permissions and config are section-based.
- **The tool never approves anything.** The analyst reviews and approves every section and prepares the Word export; the coordinator reviews the whole document and receives the export. Nobody else is in the flow for now. The Digital Payments summary email is built but is not part of it.
- **A dev-mode draft (`drafted_by` starting `local:`) never reaches a real recipient,** enforced explicitly on every path that could send or publish.
- **A genuine blocker gets a documented stub**: `NotImplementedError` with a named reason plus an `UNBLOCK` constant, surfaced to the analyst as an `unavailable` block. Never write a guessed-at implementation. The stubs below stay stubbed until real samples or access arrive.
- **The run view shows only what the pipeline really did.** Every line is a real run event (`common/run_events.py`); no simulated progress, fake delays or invented steps, in the API or the screen.
- **No authentication exists, and nothing may pretend otherwise.** Sign-in with Cytonn SSO is a stub (`backend/api/sso.py`); how Cytonn's sign-in works is never guessed.
- **Publishing is SSO-driven browser automation (Playwright), not a direct API/DB write.** No API or database access has been granted by Cytonn's team (CT). The final report is a PDF that Cytonn's CMS splits into sections: that format was stated by Clive and is not yet confirmed in writing by Cytonn. The publish step is a stub (`backend/api/cms_publish.py`, see Blocked stubs in backend/src/cytonn_weekly/CLAUDE.md) that nothing in the app can reach.
- **No file-header comments or descriptions.** A new or changed file never opens with a docblock, banner or description (no leading `/** ... */`, `//` block or `<!-- -->` explaining the file or component, in `.vue`, `.ts`, or `.py` module docstrings). Say what a file is for in the reply, not in the file. Inline comments that explain a non-obvious why are still fine. The existing headers in `frontend/src` were removed on 2026-10-26; backend docstrings were left because this file points to several of them.
- **Frontend checks use the compiler in `frontend/node_modules`** (`npm run typecheck`, or `frontend/node_modules/.bin/tsc` for a file outside the app). `npx` is never used for a package the repo does not list: `npx tsc` is not TypeScript, it fetched and ran an unrelated npm package named `tsc` on 2026-10-21, a network call nobody had approved. When a `node_modules` folder is missing, stop and ask; never fall back to `npx`.
- **Git is allowed only through the "Publishing to GitHub" procedure below and its allow-list;** every other git use is forbidden. **Commits and PRs carry no AI attribution**: no "Co-Authored-By: Claude", no "Generated with Claude Code", no session links. Commits read as authored by Clive alone.

## Publishing to GitHub

The standing procedure for committing and pushing finished work. The **expected identity** is the single author name and email of the commits already on `origin` (Clive Misiko and his GitHub noreply address), which is also what `git config user.name` and `git config user.email` return. The merge commits GitHub creates when a pull request is merged have the committer `GitHub <noreply@github.com>`; they are never pushed from here, so they are ignored when the committer is checked. Two local hooks in `.git/hooks/` (not tracked, so a fresh clone does not have them) back the procedure: `commit-msg` refuses an empty message, an attribution trailer or a tool footer; `pre-push` refuses a push to main or master, a deletion, a push that is not a fast-forward, and any commit whose author, committer or message breaks the rules. The hooks are a backstop, not a replacement for the gates below.

### B1. When to publish

At the end of every task that changed tracked files and whose own checks passed, publish the work of that task. Skip publishing if the task prompt contains the words NO PUBLISH, if the task was read-only, or if any gate in B3 fails (then stop and report why; do not publish part of a task).

### B2. Allowed git commands (nothing else)

`status`, `diff`, `log`, `show`, `rev-parse`, `rev-list`, `merge-base`, `ls-files`, `check-ignore`, `branch` (list or show-current only), `fetch origin`, `config --get`, `add <explicit file paths>`, `restore --staged <explicit file paths>`, `commit -F <file>`, `push origin <current branch>` (with `-u` only for a branch's first push), `switch -c <new branch>` (only under B4).

Forbidden: `git add -A`, `git add .`, `git add -p` or any interactive form; `reset`, `rebase`, `merge`, `cherry-pick`, `stash`, `clean`, `rm`, `tag`, `checkout`, `filter-branch`; `commit --amend`; `--no-verify` and `-n`; `--author`, `--trailer`, `-s` or `--signoff`; `push` with `--force`, `-f`, `--force-with-lease`, `--delete`, `--mirror`, `--tags`, or any refspec starting with `+`; `remote add`, `remote set-url`; any `git config` write; any `gh` command that creates or changes a PR, issue or repo. Do not open pull requests. Clive does that.

### B3. Gates before anything is staged (all must hold)

1. **Identity:** `git config user.name` and `user.email` equal the expected identity, none of the `GIT_AUTHOR_*`, `GIT_COMMITTER_*` or `EMAIL` variables are set to anything else, and the identity does not contain claude or anthropic. Otherwise stop.
2. **Tests:** the tests this task ran passed. If the task ran the full suite, it must be green. If it ran only targeted tests, say so in the publish report; do not start a full run just to publish.
3. **Remote state:** run `git fetch origin`. If `origin/<branch>` exists and has commits that the local branch does not have, stop and report. Never merge or rebase to resolve it.
4. **Line endings:** for each modified tracked file, if `git diff --numstat` shows changes but `git diff --ignore-space-at-eol --numstat` shows none, the file only changed line endings. Do not stage it; report it.
5. **Deny list:** never stage any path that matches `.env` or `.env.*` (except `.env.example`), `*.db`, `*.sqlite`, `*.sqlite3`, anything under `backend/data/`, `screenshots/`, `.claude/`, `node_modules/`, `dist/`, `__pycache__/`, `*.log`, `*.pem`, `*.key`, or timing or scratch files. If a path matches, leave it unstaged and name it in the report.
6. **Secret scan:** scan the diff of the files to be staged (for an untracked file, its full content) for the three kinds of hit below. On a hit stop, and report only the file path, line number and pattern name, never the value.
   - A private key block is always a hit.
   - A key prefix (`sk-ant-`, `ghp_`, `github_pat_`, `xox`, `AKIA`) is a hit only when it is followed by at least 16 characters from letters, digits, underscore and hyphen. A prefix mentioned in prose, in a list of patterns, or followed by a backtick, quote or space is not a hit.
   - An assignment to a name containing PASSWORD, SECRET, TOKEN, API_KEY or SMTP is a hit only when the literal value is at least 12 characters long and contains no spaces. Empty values, placeholders and short test values are not hits.

### B4. Branch

Use the current branch only if it is not main or master and no pull request from it has been merged. Once a pull request from it has been merged, start a new dated branch for the next batch from the updated `origin/main` (`git fetch origin`, then `git switch -c <topic>-<YYYY-MM-DD> origin/main`), and push that: each batch gets its own branch and its own pull request. If the current branch is main or master, create a new branch with `git switch -c` named `work/<short-topic>` (lowercase, hyphens), and push that. Never push main or master.

### B5. Grouping and commits

- Group the task's changed files into topic commits: backend, frontend, Docker and infrastructure, docs, in dependency order. A test file goes in the commit of the code it tests. Stage whole files only, by explicit path.
- Write each message to a temporary file outside the repo (the session scratchpad), commit with `git commit -F <file>`, then delete the file.
- Message format: subject in the imperative, at most 72 characters, no trailing period, then a blank line and a short plain-language body saying what changed and why. Written as the author would write it. No em dashes, no emoji, no trailers, no mention of the tool that produced it.
- Commit as Clive. Do not pass `--author`. Do not run commit with any flag that skips hooks.

### B6. Push

`git push origin <current branch>` only. If the push is rejected by a hook, auth fails, or the remote refuses, stop and report the exact message (redact credentials). Do not retry with different flags, do not ask for tokens, do not try other credentials, and never bypass a hook. Fix the cause (for example a message that tripped the rule) and try once more only if the fix is inside your own commit text.

### B7. Verify after pushing and report

- `git rev-parse HEAD` equals `git rev-parse origin/<branch>`.
- For every commit pushed: author name and email, committer name and email, and a scan of the full message for trailers. All must be the expected identity and no trailers.
- `git status` shows no remaining changes that belonged to this task.

Publish report, in plain text: branch, each commit (short hash and subject), files per commit, tests run and their result, the identity check result, the push result, and anything left unstaged and why.

## Test scope

Run only the tests a change can break. Do not run the whole suite by default.

- Always run the unit tests for the files you changed, plus typecheck, lint and build.
- Run only the Playwright spec files that cover the feature you touched, each in its own command with one worker.
- Run only the backend tests for the modules you touched.
- Run a full suite only when the change touches something shared: backend routes or schemas, shared stores or API helpers, global styles or design tokens, build or dependency files, or a component used by several pages. Say which one applies and why a full run is justified.
- Never run suites in parallel. Stop any server you started when a run ends.
- While they still fail on main, editsentence (T38) and the variants fingerprint check are not caused by your change. Report them if they still fail, but do not chase them.

## Uniform sections

The report has five sections: Fixed Income, Equities, Real Estate, Digital Payments and Focus of the Week. Every change must be uniform across all five.

- The same page structure, cards, stepper, states and wording rules apply to every section. A section differs from another only in its data, such as which documents and steps it has.
- Do not build or change something for one section only. If a change cannot apply to all five in the same round, say so before building and wait for a decision.
- Shared code stays shared. Do not fork a component or add a section-specific branch where a data difference would do.
- Tests for new behaviour run on all five sections, or through a table-driven test that loops over them. Keep the guard test that checks the five sections share one structure.
- Inputs are entered on the page itself, with Previous and Next. Never send an analyst to an old page to enter an input.
