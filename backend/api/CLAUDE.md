### Review API (`backend/api/`) and screen (`frontend/`)

`backend/api/main.py` (FastAPI) is stateless. Each write loads the review fresh from `review_store`, mutates it with the `CoordinatorReview` methods, saves, and returns the whole review shaped by `backend/api/serialize.py`. Routes:

- `GET /api/sections?report_type=&period=&kind=`: the overview of one report (no arguments: the weekly report with no label, exactly as before). It normalizes the period (422 with the reason if it does not fit) and returns `report` (type, title, normalized period, kind), `report_types` (with `period_hint`, `period_required`, `suggested_period`, `published_as`), `companion_kinds`, and per section: availability, reason/unblock/built_parts, steps, `needs_topic`/`requires_approved`/`uses_provider`, `subsections`, `charts`, and its latest run *of that report and period* (`this_week`, `current`, decision, progress, per-status counts, dev flag, week, topic). Top-level `drafting` is the draft running right now (slug, title, `report_type`, `period`, `started_at`, `elapsed_seconds`, `stale`), or null. `GET /api/report-types` returns the types and kinds alone.
- `POST /api/sections/{slug}/draft` with `{topic, text, report_type, period, kind}` (all optional; default weekly, no label): runs that section's real pipeline for that report and saves the result. 404 for a slug not in that type, 409 for an unavailable section, 422 for a bad period or a missing Focus topic, 409 (naming each section and its state) for an Executive Summary whose sections are not all approved. The Executive Summary calls no provider: they need no API key and take no drafting seat. `POST /api/reviews/draft` is the original DP-only weekly equivalent.
- `POST /api/runs` with `{section, report_type, period, kind, topic, text, provider?}` (202, `{run_id, state, position}`): the same draft as the route above, started in a worker thread and answered at once (`state` is `running`, or `queued` with its 1-based `position` when every drafting seat is taken). It goes through the same validation (`resolve_draft()`, shared by both routes), so it refuses the same things in the same words (404, 409, 422, the Q2 and Q4 period refusals, the missing-key 409), and it takes a drafting seat (or waits for one in the queue, see **Drafting seats and the queue**). `provider` is optional and only a check: the provider the screen said a draft would use; a mismatch with `CYTONN_LLM_PROVIDER` is a 409, and it never selects the provider. 409 too if that section of that report and period is already running or queued; 429 when the queue is full. `POST /api/runs/{run_id}/cancel` takes a queued run out of the queue (the run ends `run_failed` with a sentence saying nothing was drafted); a running draft answers 409 "cannot be stopped". A failure once the draft is under way (a source down, Executive Summary sections not yet approved) is the run's `run_failed` event, not an HTTP error. `GET /api/runs/{run_id}` returns the run (`status` queued/running/finished/failed, `position` while queued, `events`, `review_id`, `is_dev_draft` and `dev_mode_label` exactly as `backend/api/serialize.py` computes them for the saved review, null until it exists); 404 for an unknown run. `GET /api/runs/{run_id}/events` is a Server-Sent Events stream: every event so far, then each new one, as `event: step` with the event as JSON in `data:`, a `: keepalive` comment every 15 seconds, closing after `run_finished` or `run_failed`. See **Draft runs and run events**.
- `GET /api/reviews/{run_id}/rejected-draft-notes` (2026-10-14): the run saved just before this one for the same section, report type and period (that one run only, never older history), when it was rejected: `{run_id, decided_at, entries: [{ref, resolution, note}]}` for each item marked fix_needed or carrying a note (a note on an accepted item included); `null` when that run was not rejected, holds neither, or there is none; 404 for an unknown run. A route rather than a field on the review, because `serialize_review()` touches no database and every write returns the whole review: this way the lookup runs once, when the review is opened (`review_store.load_previous_review`, `review/model.rejected_draft_notes`).
- `POST /api/reviews/{run_id}/items/{index}/sentence` with `{action: "edit" | "remove", text?}` (2026-10-27; `weekly/sentence_edit.py`): the reviewer rewrites or removes one **flagged claim** of a drafted piece by hand, with no model and no network. It saves a NEW undecided review (new run id; the earlier one is never touched, even when approved) and answers `{review, result: {action, changed_items, earlier_run_id, was_approved}}`. Rules: **an item does not record its claim**, so the claim is found by its text (the k-th flagged-claim item with that text is the k-th claim with that text, in block order); the claim's text must appear exactly once in the piece's `body_md` and `body` (it does not when it runs across a link or a line break, or appears twice: 409 `edit_sentence_not_found`, nothing changed); the typed text is plain, one line, 1 to 600 characters (422 `edit_text_refused`; the characters `[ ] < > * \` and `\`, and a leading `#`, `+`, `-` or number and full stop, are refused, because the text goes into Markdown); an item that is not a flagged claim, or a piece carried from another section's approved review (`source_run_id`), is 409 `edit_not_possible`; a failed check or save is 500 `edit_save_failed` with a fixed sentence (the log has the cause). The figures are checked again by the same `check_section`/`build_review` as the first review, against the claim's own cited text: an edited claim keeps its `url` and `cited_text`, so a typed figure the cited text lacks stays flagged and the reviewer can Accept it knowingly. An edited claim carries `edited_at` and `was` (shown as "Edited by you, <time>" on its item and under the piece); a removal is kept in the block's `edits` and becomes a not-auto-verified item "... (removed by you)" (shown in the item list only, never in the text). `weekly/recheck.carry_marks` and `copy_chart_files` (now public) carry notes and Accept over to unchanged items. Known limit: after a removal, a later flagged claim in the same block loses its mark, because its flag names the claim by position. Block-shaped sections only; Digital Payments' own highlight items are not covered. `serialize` adds `edit_sentence` to each review item and `edits` to narrative blocks. The Word export reads `body_md` only, so an edited sentence is exported as plain text with no mark and a removed one is simply absent. Tests (written 2026-10-27, not yet run): `backend/tests/test_sentence_edit.py`, `frontend/src/lib/sentence.test.ts`, and `e2e/tests/editsentence.spec.ts` (T99 to T104; `e2e/serve_e2e.py` drafts a topic containing "bad figure" with one unsourced figure so there is a flagged sentence); the counts above were not re-taken.
- The same route with `{action: "paragraph", text}` (2026-10-27, `sentence_edit.apply_paragraph`) retypes a whole carried-forward paragraph by hand, on a `CARRIED_TEXT` item (`edit_paragraph` on the item); only Fixed Income's shilling pressure and closing outlook and Equities' closing outlook are carried blocks. The block is found by its title (the item's ref minus "(carried forward)"), which must match exactly one block (else 409 `edit_paragraph_not_possible`, nothing changed); a block with `source_run_id` (Executive Summary) is refused. Text is plain, at most 1200 characters (`MAX_PARAGRAPH_CHARS`), line breaks become spaces (so the shilling bullets flatten to one paragraph). The block gets an `edits` record, the carried flag is dropped and its item becomes not auto-verified with `EDITED_PARAGRAPH_NOTE` and `edited_at`/`was` in its context; typed figures are compared with nothing. The Word export drops the red carried note once the paragraph has been edited (`export.py`, `if not block.get("edits")`) and prints any block that `continues` it (Fixed Income's borrowing sentence) in the same paragraph, under one heading. The next week's carry-forward reads the published issue on cytonnreport.com, never this tool's review.
- `GET /api/reviews/{run_id}`, `GET /api/reviews/latest`, `PATCH /api/reviews/{run_id}/items/{index}` and `POST .../accept-clean` (kept for stored data; the screen no longer calls them), `POST .../decide`, `GET /api/config` (provider, dev mode, whether a draft spends API budget, and `provider_problem`: why a draft can't run, e.g. missing AWS settings in bedrock mode; both draft routes refuse such a draft with 409 before taking the slot or fetching anything), `GET /api/health`.
- `GET /api/inputs/weekly/{week_ending}` (what has been received for the week), `PUT .../{slot}?filename=` (upload: the file is the request body; 413 over the size limit, 422 with the reason if it is not the slot's document), `DELETE .../{stored_name}`, `POST .../cbk_bulletin/fetch` (404 if CBK has not published that Friday's issue), `PUT .../notes` (the bidding range, the previous issue), `GET`/`PUT .../analyst?section=` (the weekly analyst inputs form; see **Weekly analyst inputs** in backend/src/cytonn_weekly/weekly/CLAUDE.md). `{week_ending}` must be a Friday (422 otherwise). See **The weekly report's inputs** in backend/src/cytonn_weekly/weekly/CLAUDE.md.
- `GET /api/equities/companies` (the listed banks and insurers of the weekly Equities and whether each website is set, with the per-company caps).
- `GET /api/export/weekly?period=` (each weekly section's state, `ready`, `flagged_accepted_on_approval`, the dev mark) and `POST /api/export/weekly?period=` (the `.docx`; 409 naming each section unless all are approved).
- `GET /api/notable/{section}?week_ending=&report_type=`, `POST /api/notable/{section}/decisions?week_ending=` and `DELETE /api/notable/{section}/decisions/{suggestion_id}?week_ending=` (2026-10-14): the "Notable this week" suggestions for a weekly section and week, and the analyst's decisions on them. The real registry is empty, so the real app returns an empty list. See **Notable this week** in backend/src/cytonn_weekly/notable/CLAUDE.md.

The API, not `review_store`, refuses edits to a decided review. Writes share one lock. **At most `CYTONN_DRAFT_CONCURRENCY` drafts that call the model run at a time across every section of every report** (default 3, 1 to 6): `backend/api/draft_slot.DraftSlot`, a counting limiter, one per `create_app()`, in process memory. It records which sections hold a seat and since when, which the overview shows (`drafting_list`, and the older single `drafting` key, the longest-held seat, kept for one release). The synchronous draft routes get a 409 naming the longest holder when every seat is taken; only `POST /api/runs` queues (see **Drafting seats and the queue**). A crash releases a seat (the release is in a `finally`, including on `BaseException`), and so does a restart, because seats aren't persisted. A *hang* would not release one: each call has only a per-read timeout and no overall deadline. So a claim older than `DRAFT_STALE_AFTER_SECONDS` (1 hour) is treated as stuck, and a draft that finds every seat taken takes the oldest stale one over. Python can't kill the stuck thread; if it finishes later, `release()` returns False and its result is **discarded, not saved**, so an abandoned run never lands over its replacement. A draft is otherwise saved server-side as soon as it finishes, so a dropped connection never loses a paid run. The API has no authentication.

### Draft runs and run events (`common/run_events.py`, `backend/api/runs.py`)

Every draft builder (each section's `build_*_review`, plus `draft_highlights`, `draft_outlook`, `draft_pieces`, `check_digital_payments` and `check_section`) takes an optional `on_event` observer, default None. With None a builder does exactly what it did before (tested per builder: same review with no argument, with None, with a recording observer and with an observer that raises). An observer is called as `on_event(kind, label, detail=None, counts=None)` and only ever through `run_events.emit()`, which swallows and logs whatever it raises, so an observer can never break a draft. `DraftContext.on_event` carries it through the registry, which passes it to a builder only when it is set (tests monkeypatch builders with fakes that take no such argument).

`RunEvent` has `seq` (from 1), `kind`, `label`, `detail`, `counts` (`clean`, `flagged`, `not_auto_verified`: the review model's own statuses) and `at` (UTC ISO). The only kinds: `run_started`, `source_started`, `source_finished`, `source_failed`, `piece_started`, `piece_finished`, `part_skipped`, `check_started`, `check_finished`, `run_finished`, `run_failed`, `sources_looking`, `sources_found`, `sources_search_unavailable` and `retrying`. What emits what:

- `run_started`, `run_finished`, `run_failed` come from the API's worker (`work_run` in `backend/api/main.py`), never from a builder: a run is finished only once its review is saved. `run_finished` carries the saved review's items per status; `run_failed` carries the error as one line (`failure_message()`: no traceback, and any configured secret an error quotes is redacted).
- `source_*`: one fetch a builder makes (`run_events.fetch_source`): Yahoo Finance, afx.kwayisi.org, the Ibuka summary, each period's CBK T-bond results, KNBS's CPI release, each company's Yahoo price history in the Markets Reviews. A failure a fetcher isolates to one row (a share page, one CBK PDF, one ticker) is a `source_failed` of its own and the draft goes on; a fetch that raises is `source_failed` and then, as before, the builder's error (so `run_failed`).
- `piece_*`: one drafted piece or one table. A headline is not known until the piece is drafted and the two events must share a label, so a narrative piece is labelled with its brief's label or its company (the piece's stored `topic`) and `piece_finished` carries the headline in `detail`. A table only ever finishes (it is built in one step from rows already fetched).
- `part_skipped`: each `unavailable` block, with the stub's blocked reason in `detail`. It also closes the `piece_started` of a theme or company whose search found nothing to draft (`detail` says so), because no other kind says "started, and nothing was drafted".
- `check_*`: one table's exact-match check or one piece's claims. `check_finished` counts are the review items that check produces, so over a run they add up to the review's own counts once the `unavailable` parts (one flagged item each) and supplied text (one unverified item) are added (tested for every builder).
- Nothing else. The Executive Summary has no step of its own (composed in one step), so a run of it is `run_started` then `run_finished` (or `run_failed`).

`backend/api/runs.py` holds the live runs in a dict guarded by a lock, and live runs stream from it; **since 2026-11-16 every status change and event is also written through to the tables `draft_runs`, `run_events` and `draft_usage`** (`run_store.RunStore`; a storage failure is logged by class name and never fails a draft). A run the dict no longer holds (more than 50 ended ones are not kept in memory, or any run after a restart) is read back from storage by `GET /api/runs/{id}` and its event stream, with the same shape as before. At startup (`create_app`'s startup hook, so under a real server and not in a bare `TestClient`) every run still `queued` or `running` in storage becomes `interrupted` with a closing `run_failed` event saying the tool was restarted (`run_store.interrupt_active`; it assumes one API process); the draft's Bedrock `usage` is saved in `draft_usage` against its run. The synchronous draft routes have no run, so they write none of this. `report_jobs` and `job_messages` (`jobs.py`: one job per report type, period and section, its messages in order, and the three `CYTONN_JOB_*` limits it was opened with) are used by the analyst chat's loop (see backend/src/cytonn_weekly/agent/CLAUDE.md), which enforces the limits; no route or screen uses them yet. **One run per (report type, period, section) at a time** (running or queued; a second start is a 409 saying it is already being drafted or is queued), and the drafting seats still apply on top to every section that calls a provider. A run that held a seat past the stale limit and was replaced ends `run_failed` and saves nothing, as on the draft route.

**The run view shows only real events.** No simulated progress, no timers, no minimum display times, no invented steps: every line on `/runs/{run_id}` is one event from the list above, worded by the fixed templates in `frontend/src/lib/run.ts`. If nothing is happening, nothing on that screen moves. Keep it so when adding steps: emit where the pipeline really does the thing, never in the screen.

### Drafting seats and the queue (2026-11-06; `api/draft_slot.py`, `api/runs.py`, `api/main.py`)

Several analysts may draft at once, each a different section or report. **The API stays one process with threads; never add uvicorn workers or a second replica.** The seats (`DraftSlot`), the waiting queue (a `deque` in `create_app`) and the run registry are all plain objects in process memory: a second worker would have its own seats, its own queue and its own idea of which runs exist, so the limit would be per worker, a queued run could start twice and a run id would 404 on the other worker. If throughput ever needs more than one process, the seats, the queue and the registry move to PostgreSQL first.

- **Seats.** `CYTONN_DRAFT_CONCURRENCY` (default 3, an integer from 1 to 6; a bad value logs one warning and uses 3) is the number of drafts that call the model at once; the Bedrock quota and the api container's memory are what bound it. Only sections where `uses_provider(spec)` is true take a seat (the Executive Summary never does). A seat held past the stale limit (1 hour) is taken over by the next draft that finds every seat taken, as the single slot always was.
- **Queue.** `POST /api/runs` answers 202 with `{run_id, state: "running"|"queued", position}`. With every seat taken (or someone already waiting) the run joins a bounded FIFO, `CYTONN_DRAFT_QUEUE_MAX` (default 20, 0 to 200); beyond it a 429 says the queue is full and nothing is registered. A finishing, failing or crashing run gives its seat back in a `finally` (before the database save, as before) and starts the next queued run; each run is its own thread with its own try/except, so one failure never stops another. Lock order is always `seats` (the queue lock) then the limiter's mutex. **A queued run is a registry run with `status: "queued"` and no events**; it becomes `running` (and records `run_started`) when it gets a seat, and its elapsed time counts from then. `POST /api/runs/{id}/cancel` removes a queued run (it ends `run_failed`: "Cancelled while it waited for a drafting seat... Nothing was drafted."); a running one is 409 "cannot be stopped", an ended one 409. A restart loses the queue (and the draft threads), but not the runs: each run that was queued or running is marked `interrupted` in storage at the next start and reads back as stopped (its closing event is a `run_failed`); only an id that was never stored is a 404 with `find_run`'s sentence.
- **The synchronous draft routes** (`POST /api/sections/{slug}/draft`, `POST /api/reviews/draft`) take a seat and never queue: with every seat taken they answer 409 `draft_busy` naming the longest holder. They have no `Run`, so no source-route refusal follows them.
- **`/api/sections`** returns `drafting_list`: one entry per running or queued draft (`section`, `title`, `report_type`, `period`, `run_id`, `state`, `position`, `started_at`, `elapsed_seconds`, `stale`, `step` = the last event it reported), plus, for a section whose newest run failed, a `failed` entry with `reason` (kept in memory until that section is drafted again). The older single `drafting` key (the longest-held seat) stays for one release.
- **What still refuses while a draft runs** (route audit, 2026-11-06). Before, `refuse_while_drafting` refused any source change while ANY draft ran. Now each refuses only while a running or queued draft that reads that piece (`Run.piece_keys`: its `pieces_for` subjects filed under their Friday) exists, and ignores a running draft past the stale limit: `POST /api/sources` (add or fetch), `DELETE /api/sources/{id}` and `POST /api/sources/gather` ("Look again"). The weekly inputs routes (uploads and removals of workbooks, KCB reports, the CBK bulletin and its fetch, notes, the analyst form, chart uploads), approve, reject, resolve, edit-sentence and export never refused during a draft and still do not; their shared files are now written atomically (below). A weekly input two sections read (the CBK bulletin is read by Fixed Income and Equities) is not locked against a running draft: the file is replaced atomically, so a draft reads either the old file or the new one whole, and the manifest records which.
- **Shared files** (`common/atomic.py`: `write_atomic` writes a temp file and `os.replace`s it; `locked` and `key_lock` serialise read-modify-write). Fixed because two sections running together could race: the weekly inputs `manifest.json` and `notes.json` (two uploads at once lost an entry), the analyst form, `charts.json` and chart images, the CBK results cache `index.json` (two drafts held stale in-memory copies and overwrote each other; it is merged under a lock before it is written), the OCR cache (a half-written JSON broke the next read, and two drafts of one PDF ran the OCR twice; one lock per file), the bond issues cache and the Exa caches. Already safe: the sources store (one lock, atomic manifest) and the chart store (exclusive create).
- **Memory.** `deploy/docker-compose.server.yml` gives the api `mem_limit: 768m`; the base `docker-compose.yml` sets none. The OCR of the NSE price list (Equities only) and pdfplumber on CBK and KCB PDFs are the heavy steps, and with three seats they can overlap. This is not measured: if the box is short of memory, run with `CYTONN_DRAFT_CONCURRENCY=2` or raise `mem_limit`.
- **The screens.** A Draft button (start screen, Draft again on a card) is off only for a section that is itself running or queued, with "Being drafted now" or "Queued, 2 ahead" (`lib/drafting.ts`: `draftingFor`, `ownBusy`, `draftingStatus`); another section drafting never holds it. The overview cards show Queued, the running draft's step, "Draft failed" with its reason, or the usual state once a review exists; the rail shows Queued and Being drafted; the run view of a queued run shows its place, polls it every two seconds, moves to running by itself and offers "Cancel this draft".
