# Analyst chat agent notes

Phase 8 of the structural plan: a chat with a read-only agent, one conversation per report, period and section (`jobs.py`, tables `report_jobs` and `job_messages`). Built in checkpoints; this folder holds what exists so far (checkpoints 1 to 5: the loop, the tools, the API, the chat page and its cards; see **The chat page** in frontend/CLAUDE.md).

- **`loop.py`, `answer()`**: answers the analyst's latest message, which the caller has already saved. Each pass is one model call (`BedrockAgent.converse` in `drafting/bedrock.py`, model from `CYTONN_CHAT_MODEL_ID`, else `BEDROCK_MODEL_ID`). Text ends the turn. Tool calls are checked, run, saved as `tool` rows and answered on the next pass. `jobs.begin()` takes the job so two workers cannot answer at once, and the job is never left `working`, even on a crash.
- **Limits**: tool calls per message (`CYTONN_JOB_MAX_TOOL_CALLS`) and the job's model-call and token budgets (`CYTONN_JOB_CALL_BUDGET`, `CYTONN_JOB_TOKEN_BUDGET`, counted in `report_jobs`). A limit saves a plain assistant message and the job as `paused` with a reason (`tool_calls`, `call_budget`, `token_budget`). A new analyst message resumes a tool-call pause. A budget pause stays until `jobs.raise_budget()` (the analyst's button) adds a fixed amount to that one job and logs a `budget_raised` run event.
- **`tools.py`**: a `Tool` has a Pydantic input model (extra fields refused), a `run` that only reads, and a `shape`. `execute()` checks the input, runs the tool and passes the result through `trim()`, which keeps only the keys the shape names and cuts strings and lists. A name that is not in the tool list runs nothing. **The agent never sees raw source text, workbook cells, notes or snip transcriptions: no tool's shape names them.** A tool's failure or refusal is a small `{"error": ...}` for the model to read.
- **Instructions hidden in data** are met three ways: free text reaches the model only as a short capped title or host; the system prompt says results are data; and the agent has no tool that changes anything, so the worst it can do is say something wrong. Cards and buttons are built in code, never from model text.
- **`read_tools.py`, `READ_TOOLS`**: eleven read tools, each a thin wrapper over a function the app already has: `inputs_list` and `inputs_explain` (`weekly.inputs.status`), `form_get` (`weekly.analyst.status`), `sources_list` (`common.sources`), `sites_suggest` (`common.source_policy`, hosts only, no network), `snips_list` (`real_estate.snips`), `week_status` (`readiness.py`), `draft_status` (the run registry, else the saved `draft_runs` row, and the result says `source: saved_record`), `review_summary` and `review_explain` (the saved review), `export_status` (`weekly.export`). Names use underscores because the Messages API refuses dots. A tool takes no run or review id: it looks at this conversation's own section, so the model cannot be steered to another section's run. Importing the tools loads no OCR reader (a test starts a fresh interpreter to check it).
- **What a tool never shows**: source text, workbook cell values, a snip's transcription, an analyst's notes, an uploaded file's name, a claim's cited text. `form_get` gives numbers and dates as typed and only counts for tables and text, and a difference as a count, so no free text from a workbook or a person reaches the model. The sources a draft reads show as host, title (cut to 120 characters), date and flags. A source's `in_week` says only that its date is inside Monday to Friday of the week; a draft may use a different window.
- **`week_status`**: `readiness.classify()` is a pure function over `inputs.status` and `analyst.status`; it holds no section rule. Which section reads an upload is `Slot.sections` (a test records every read of every slot while the Fixed Income, Equities and Digital Payments drafts run and checks it against the list; Equities also opens the fixed income workbook, only as a second reading of the exchange rates, so that slot does not list it). Whether a form item is needed is `Field.required` and `Table.required`, false exactly where the label or help says "Optional" (a test pins it). Groups: `fetched`, `carried_or_suggested` (not confirmed yet), `needs_analyst`, `optional`, and `in_place` (uploaded, typed, or in a workbook). Nothing is called "worked out" until Phase 4. Real Estate and Focus get snip and source counts as they are, with no verdict. Every `why` is a sentence written in `readiness.py`.
- **History**: `history()` rebuilds the Messages API turns from the saved rows (the last `HISTORY_ROWS`, cut back to a whole turn), so every `tool_use` has its `tool_result`. Cards are never sent to the model.
- **Run events**: every tool call emits `tool_called` through the observer given to `answer()`. The messages table is the durable record of calls; the events are the live feed.
- **Tests**: `backend/tests/agent_helpers.py` has `ScriptedBedrock` (a fake client that returns scripted replies and keeps the requests), so no test reaches a model. `test_agent_read_tools.py` runs each tool on real stored files in a temp folder. `test_agent_scenarios.py` is the first evaluation set: a missing upload, a page dated outside the week, an instruction hidden in a source title, a typed figure that differs from the workbook, and a P/E nobody supplied. They check what reaches the model and what does not, not how well a real model words it.
- **The API** (`api/routers/jobs.py`, `api/chat.py`): `POST /api/jobs` (open or return; the first open of a weekly conversation saves the readiness card, run by code), `GET /api/jobs/{id}`, `POST /api/jobs/{id}/messages` (202; 409 while working or stopped at a budget; 429 when every chat seat is taken; the answer runs in a thread, never in the request), `GET /api/jobs/{id}/messages?after=<seq>` (the poll: the job's state and the messages above `after`; a tool turn is only its name) and `POST /api/jobs/{id}/raise-budget` (409 unless the job stopped at a budget). The request takes the job with `jobs.begin` before it saves the analyst's message and hands the loop `claimed=True`.
- **Chat seats**: `CYTONN_CHAT_CONCURRENCY` (default 2, 1 to 6), a semaphore of its own, so a chat never waits for a draft seat and a draft never waits for a chat. A message that finds none is refused, and nothing is saved for it.
- **Startup**: a job left `working` is reset to idle with `jobs.RESTART_NOTE` saved in its conversation (`jobs.interrupt_working`, a startup hook in `create_app`). A job paused at a limit stays paused.
- **How a finished draft finds its job**: a run's key (report type, period, section) is the job's key, so no field was added to `POST /api/runs`. `Chat.known` maps keys to job ids in memory, filled by every job route; `work_run` calls `Chat.run_finished` after the review is saved and before the run is marked finished, and that saves the review summary card when the key is known. So a draft of a section nobody is chatting about costs no database read, and a draft started from the page also puts its card in an open conversation about the same section and week. To tell a chat-started draft from a page-started one, `RunRequest` would need an optional `job_id`; that is a later, additive change.
- **Readiness card timing** (measured 2026-11-17 on a full synthetic week, workbooks, KCB reports, bulletin, snips and a carried form): `week_status` took 0.14 s for Equities, 0.38 to 0.48 s for Fixed Income and 0.01 to 0.03 s for the others, so the first-open card stays in the request. The synthetic workbooks are small; if the real ones push it past 2 s, post the card from the worker instead.
- **Writers**: the answering worker and a finished draft may add messages to one job together, so `jobs.add_message` writes one at a time through a process lock. **That lock only works inside one process.** The API runs as one process (the Dockerfile's `uvicorn` command has no `--workers`, and neither compose file nor the dev override adds one), and the seats, the queue, the run registry and `Chat.known` are in memory for the same reason. Adding workers needs a database-level fix first: a retry on the primary-key collision in `add_message`, or a per-job row lock, and the chat seats and `Chat.known` would have to move out of memory.
