# Review notes

Moved word for word from the root CLAUDE.md in the Phase 6b restructure; nothing in it was edited.

### Two content shapes, one review model

Every section produces a `CoordinatorReview` (`review/model.py`, section-agnostic despite its path) persisted by `review/store.py` under the section's slug, with its `report_type` and `period` (fields on the review, columns in `coordinator_reviews`, fixed at the first save; the API stamps them on every draft). The columns were added by `sections._migrate()`, which `init_db()` runs after `schema.sql`: `ADD COLUMN` with defaults, so every older row reads back as a weekly review with no label, unchanged (tested on an old-schema database and on a byte copy of the real `backend/data/app.db`, whose hash is checked unchanged). A fresh table and a migrated one have identical columns.

- **Digital Payments** has its own pipeline and content shape:
  `fetcher.fetch_digital_payments()` (raw rows) → `highlights.draft_highlights()` / `draft_outlook()` (via a provider) → `compose_section()` → `digital_payments.checks.check_digital_payments()` → `digital_payments/review_run.build_coordinator_review()`. `digital_payments/review_run.build_digital_payments_review()` wires these and is the only place that does. Content: `items` (highlights), raw table rows, `outlook` with `stats`.
- **Every other section** (including the Markets Reviews' Digital Payments, which is block-shaped so its period columns never touch the weekly table the Word summary reads) uses generic **blocks** (`review/blocks.py`): `table` (columns with `fmt`/`decimals`, display `rows` stored *beside* raw `source_rows`, `source`), `narrative` (a drafted piece with claims, links, `drafted_by`), `unavailable` (a real report part the tool can't draft yet, with `reason` and `unblock`), and `supplied` (text the analyst pasted, carried verbatim; one `supplied_text` review item, never verified). Since 2026-10-14 that item is also checked for web links (`common/links.find_links`, `review/blocks.supplied_item`): text analysis only, nothing is fetched, opened or resolved, and the text is never changed. A certain link (http:// or https://, www., a markdown or HTML link, a shortener with a path, a bare domain with a query) makes the item `flagged`, one `Flag` a hit (kinds `link` and `possible_link`, scope `supplied`), shown as plain text with its 1-based position; only possible hits (a bare domain with a known top-level domain, with or without a path; an email address; "click here" and the like with no link in the text) leave it not auto-verified with one line each under the note. Neither blocks approval. The serializer picks the shape by `"blocks" in content`, not by slug. `review/checks.py` exact-matches every numeric table cell using DP's own `check_figure` (same mismatch / missing / sources-disagree semantics; `check_table_block` takes an optional `extra_sources` mapping, `{(row subject, column key): [SourceValue]}`, and hands each list to `check_figure` unchanged, but no caller passes it because no second source exists yet), checks each claim's figures against its cited span, and turns each `unavailable` block into a flag. `review/blocks.build_review()` makes one `ReviewItem` per table row, claim, and unavailable part, so an analyst can't approve a section without explicitly acknowledging what's missing. Each section's `review_run.py` (equities, real_estate, focus) runs fetch → draft → compose → `check_section` → `build_review`.
- **Computed paragraphs and the checking policy** (`common/computed.py`, used by the weekly Fixed Income and Equities). Two more block kinds: `computed` (a paragraph of fixed wording around figures the tool worked out; each figure is stored with its `inputs`, each input's `origin` and `source`, and the `expr` that makes it) and `carried` (text copied from the previous issue). `check_figure_record` works every figure out again from its inputs with exact decimal arithmetic, rounds half up to the display precision and requires the printed figure to equal it and to appear in the paragraph. One review item per figure. The policy, applied everywhere:
  - **Computed figures carry their source rows and are exact-matched** (clean when made only of published inputs).
  - **A figure read from a typed workbook cell is shown as "analyst input from <workbook> <sheet>!<cell>" and is not auto-verified, never clean**; so is anything worked out from one. A published source that agrees with a typed cell verifies it; one that differs is a "sources disagree" flag.
  - **An OCR'd figure must agree with a second source.** Confirmed by a published one (KCB's report, afx's own week and year changes while afx's page is still that Friday's) it is clean; agreed only by the analysts' typed value it is not auto-verified; alone, or disagreeing, it is flagged.
  - **Text carried forward from the previous issue is always flagged "carried forward, edit before approving".** Each carried paragraph is looked for in its own section of the previous issue (`_carried` in `fixed_income/weekly.py`): the two closing outlooks in Fixed Income and Equities only. The shilling-pressure paragraph alone is also looked for in `kenya-macro-economic-review` when Fixed Income has none (2026-10-13), because a Markets Review prints the shilling under "The Kenyan Shilling:" in its Kenya Macro section (issue 892, the Q3'2026 review); Fixed Income wins when both hold it. Text found there carries `section` and a `note` on `carried_from`, and its flag adds "taken from the Kenya Macro Economic Review of issue <id>, a Markets Review, not from its Fixed Income section; check the dates and the period it speaks of". When neither holds it, the unavailable part names the sections searched. Its bullets stop at five lines, at a line with "forex reserves" in its first 40 characters or "forex reserves increased/decreased" anywhere, at "Weekly Highlights", at "Key to note", or at a heading (eight words or fewer, ending in a colon); the opening line's own colon never stops it. When the lookup passed over a stripped twin to reach the issue it used (see **Parsers**, `previous_issue.py`), `carried_from` also holds `kind` (`weekly` or `review`) and `skipped` (the ids passed over), and the flag adds "the lookup skipped issue <id> on cytonnreport.com, a copy of this issue with its charts stripped; the text is from issue <id>, a weekly" (a Markets Review when it is one). **When the issue used is a Markets Review (`Issue.kind == "review"`: it has a Global Markets or Sub-Saharan Africa section, so the markets outlook issue 843 counts too), with or without a skipped twin, `carried_from` holds `kind` and the flag adds "the text is from issue <id>, a Markets Review (a quarterly, half-year or annual review), not a weekly; check that it speaks of this week's period and not only of the review's"** (Fixed Income outlook, Equities outlook and shilling alike), except where the kind is already said: a skipped twin's sentence names it once, and text taken from the review's Kenya Macro section carries a `section` and a `note` that already say "a Markets Review". Of the 37 weeks replayed on 2026-10-15, four review weeks gain the sentence (23 Jan, 10 Apr, 10 Jul, 9 Oct) and the other 33 keep their text exactly (the 9 Jan flag already names the review once through its twin sentence). When the issue used is a weekly and no twin was skipped, nothing is added and `carried_from` keeps its three keys. On the review screen the carried block's notice shows the issue used and its date, and the flag on its review item carries the rest; the inputs panel's "Previous issue (optional)" box only holds what an analyst typed and shows nothing the lookup chose.
  - A table block can say the same about its rows: `row_origin: "analyst_input"` (or `_origin` on one source row) makes a row that passes its exact-match not auto-verified; `second_sources` are handed to the table check; a column with an `expr`, and a row's `_derived` cells, are worked out again from the row's own raw fields.
  - A paragraph figure in PLAIN_PCT, PCT or POINTS that is not zero but rounds to zero at its precision is shown to three decimals (`a_figure` sets `decimals` to 3, and the checker reads the same `decimals`, 2026-11-17); a table's cells are not changed (`check_table_block` reads each column's fixed `decimals`, so a column that can hold such a change, such as the Eurobond table's Weekly Change row, the Universe of Coverage's change columns and the index tables, would need that check to take the cell's own precision first). Builders must compute derived figures with `computed.evaluate` (decimal), never float arithmetic: 399.0 against 400.0 is exactly -0.25%, which rounds half up to (0.3%), and a float gives -0.2499... (the checker caught this on the real Universe of Coverage).
- **Narrative drafting outside DP** goes through `drafting/`: `NarrativeProvider` is DP's provider contract with a *brief* (theme + preferred domains) in place of a company, and it returns DP's `HighlightResult` unchanged. `drafting/drafter.draft_pieces()` tries briefs in priority order up to a target and reports a shortfall rather than backfilling; its `window=(start, end)` replaces the report week (the Markets Reviews pass the period). A brief's `report` and `window` fields name the report and the search window in the prompt; their defaults (`"weekly"`, `"report week"`) keep the weekly prompts word for word (tested). `periodic.common.period_brief()` builds a period brief with no forced opener, since the reviews open their subsections variously. `drafting/factory.get_narrative_provider()` honours the same `CYTONN_LLM_PROVIDER` switch and DEV MODE banner as DP's `drafting/factory.py`.
- **Shared formatting:** `common/formatting.py` (`fmt_value`, `format_rows`, `round_half_up`, `clean_pdf_number`) is the one place display strings are made outside DP. Each table column declares `fmt` (`text`/`number`/`price`/`pct`/`multiple`) and `decimals`, and the checker reads the same column definition, so display precision and check precision can't drift. `common/http.py` is the injectable `get` every fetcher defaults to.

Things that bite if you don't know them:

- **DP's `compose_section()` holds raw fetcher rows, not display strings.** Anything user-facing for DP must call `fetcher.format_table_rows()` first. The DP Average row is not a stored row; it comes from `outlook["stats"]`. (Block-shaped sections store display rows, so they don't have this trap.)
- **`CheckReport` records only flags and a count of figures compared, never what passed.** "Clean" items are everything no flag points at, so a skipped scope would read as all-clean (see Open items).
- **`ReviewItem.status` vs `resolution`:** status is the machine's view (`flagged`/`clean`/`not_auto_verified`); resolution is the analyst's (`accept`/`fix_needed`), kept in storage and shown read-only on older reviews, but no longer set on screen (2026-11-14: the Unresolved / Accept / Fix needed control, the item note box and "Mark all clean as accepted" are gone; a section is approved or rejected as a whole). `decide("approved", acknowledged_flagged)` needs a draft (`is_approvable` is "the review has items") **and, since 2026-11-16, the server enforces the acknowledgement**: with flagged items the approval is refused (`FlaggedNotAcknowledged`, a `ValueError`; the route answers 409 `review_not_decidable`) unless `acknowledged_flagged` (the optional field of `POST /api/reviews/{run_id}/decide`, an integer from 0) equals their count now, so a stale screen or a guess cannot approve; with none flagged the field is not needed. On an acknowledged approval each flagged item with no resolution becomes `accept` with the note "Accepted as part of approving the section, at (UTC) <decided_at>." (`ACCEPTED_ON_APPROVAL`); an item already resolved is left alone. The screen still asks once, naming the count and the first three, and `lib/session.ts` sends the count of flagged items of the review on screen, which is the count the dialog named; `export_status()` gives each section `flagged_accepted_on_approval` (`CoordinatorReview.accepted_on_approval()`), 0 unless approved; the Word export is unchanged. `cms_publish` and the Digital Payments delivery path do not call `decide` and refuse what they did; `"rejected"` is always allowed; a decision is made once. **Removing a finding** (`POST /api/reviews/{run_id}/items/{index}/remove-finding`, `sentence_edit.remove_finding`): "Remove this finding" on a claim of a model-drafted piece (a Digital Payments highlight or a narrative block) saves a new undecided review without the whole piece, its claims and its sources, so it leaves the review, the section summary, the Word export and the Digital Payments Word summary; the piece is listed under a collapsed "Removed findings" note marked "Removed by you", only a redraft brings it back, and a piece carried into an Executive Summary is refused (problem codes `finding_not_possible`, `finding_not_found`, `finding_save_failed`). There's no way to edit a drafted value in review, so approved means "accepted as drafted". A claim that passes the figures-in-cited-span check is still `not_auto_verified`, because its wording is never verified.
- **A decided review is frozen:** `save_review()` raises `ReviewAlreadyDecided` if a stale copy tries to change it. Saves are insert-then-update on `run_id`.
- **`load_latest_review()` returns the newest review whether or not it is decided**; consumers check `.decision`. `write_latest_summary()` and the send script deliberately use the latest, not the latest approved, so a newer unapproved draft blocks summarizing an older week. It takes `report_type` (default **weekly**) and `period` (default `None`, any period of that type), so the weekly Word summary and delivery can never pick up a newer quarterly Digital Payments review (tested).
- **The Word summary and email delivery are Digital-Payments-shaped.** `summary.py`, `delivery.is_dev_mode_review()` and the email subject all read DP content (`items`, `outlook`, the stock table). There's no summary for block-shaped sections yet; `send_weekly_summary.py` only accepts slugs in its `SUMMARY_SECTIONS`. They are also weekly-only by an explicit guard: `summary.require_approved` first calls `require_weekly`, so `write_summary`, `write_latest_summary`, `email_summary` and `deliver_latest_summary` refuse any non-weekly review with `SummaryNotAllowed` (the two `*_latest` functions take `report_type`, default weekly), before any file is written or SMTP is touched (`backend/tests/test_summary_report_type_guard.py`).
- **Dev mode:** library code reads `os.environ` only; entrypoints call `env.load_env()`. With `CYTONN_LLM_PROVIDER=local`, every narrative piece carries `drafted_by: "local:<model>"`, the screen shows a DEV MODE ribbon, the Word doc carries a NOT FOR CIRCULATION banner, and delivery refuses to send. Any new path that could reach a real recipient must check `drafted_by` itself rather than assume an existing guard covers it.
