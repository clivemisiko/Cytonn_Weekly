# History store notes

Phase 4 of the structural plan (started 2026-11-18). The tool keeps every weekly series itself, one current point per series and date, with where each point came from. Checkpoint 1 is the tables and `store.py`; **nothing calls the store yet**.

- **Tables** (`series`, `series_points`, in `schema.sql` and `schema_postgres.sql`, `CREATE TABLE IF NOT EXISTS` like the others). A series is `(key, subject)` (subject is a fund or company, `''` for none) with one unit, fixed for good (`store.UNITS` is the notable library's units plus `kes`). A point holds its value as decimal text, `origin` (fetched, typed, worked_out, carried, workbook_import), `source_kind` and `source_ref` (a source id, a form field or table key, `<sheet>!<cell>`, or the working), `superseded_by` and `confirmed_by`/`confirmed_at`. A partial unique index allows one point with `superseded_by IS NULL` per series and date.
- **Corrections never edit a value.** A different value adds a new point and sets the old one's `superseded_by` to it, in one transaction (the old point points at itself for a moment to free the unique slot). The same number again changes nothing, except that a confirmed write over an unconfirmed point of the same number is a new point (a typed value over a suggestion).
- **A point is used only once confirmed** (`current()` hides the rest unless asked), the same rule as `analyst.usable_form`. `confirmed_by` is `"analyst (form)"` for form saves and `"workbook import"` for imports (`store.FORM`, `store.IMPORT`).
- **Confidential series** (the P/E series, the fund table, placements) live in the database and data folder only: never in the repo, tests, docs, logs or reports. Tests use invented series. No message or log line holds a value.

## The importer (checkpoint 2, `importer.py`, `scripts/import_history.py`)

Reads the analysts' workbooks once for their history. **Nothing calls it from the app**; it is a script. Each sheet is found by name and each row by its date in column A or its label (the existing readers' helpers, `Sheet.find`, `_weekly_rows`, `_price_columns`, `read_eurobonds`), never by a fixed row.

- **Series imported** (`importer.CATALOG`): from the equities workbook, `eq.turnover.day|week|ytd` and `eq.foreign.day|week|ytd` (USD mn; a weekly point is dated the week's Friday), `eq.pe` (multiple), `eq.dividend_yield` (percentage as printed, the workbook's fraction times 100), `eq.price` (KES, one subject per company, from the Universe of Coverage "Price as at" columns); from the fixed income mastersheet, `fi.interbank.volume|rate` and `fi.eurobond.yield` (subject: the issue). **Not imported:** the fund table and placements (the store starts empty for them; earlier tables can be imported if the team sends them), index levels (out of Phase 4), reserves and remittances (no unit yet), the T-bill and borrowing sheets (CBK's files rebuild them), the AVERAGE rows (worked out from the points).
- **Values** are the workbook's saved numbers, rounded half up to 8 decimals (workbook floats carry noise) and stored without trailing zeros. A weekend-dated row in a daily sheet is set aside; in the P/E and dividend yield sheet it is kept, because the workbook's AVERAGE counts it (two Saturday-dated rows in 2015) and the store's mean over the AVERAGE window must equal that cell. A row dated after today is set aside. A date twice with different numbers keeps neither.
- **Dry run first.** `python scripts/import_history.py FILE... [--db SCRATCH.db]` prints the database it would use (kind, never the URL), then per series: rows seen, points, subjects, first and last date, new / same / different against the store, and the rows set aside with the reason. **It prints no value.** `--apply` adds the points the store does not hold, as `workbook_import` points with `confirmed_by` "workbook import" and the cell in `source_ref`, in one transaction and a few multi-row statements (`store.add_new`: a round trip to Supabase costs about 200 ms, so a point at a time would take hours). A point the store already holds, same number or not, is never touched, so a re-run adds nothing new and an analyst's later correction survives it.
- **On the server:** the real import runs in the api container on the workbook already uploaded there (`<data>/inputs/weekly/<Friday>/equities_workbook.xlsx` and `fi_workbook.xlsx`): `docker compose exec api python scripts/import_history.py <those paths>` for the dry run, then again with `--apply` once the dry run counts are approved. The container has no `.env`; its database comes from its environment, and with `CYTONN_REQUIRE_POSTGRES=1` it can only be PostgreSQL.
- **Checked on the 13 Nov equities workbook and the 14 Nov mastersheet (2026-11-18):** the points for the week ending 13 Nov equal what the existing readers read (turnover and foreign week and year to date, the daily turnover, P/E, dividend yield, the 13 companies' prices on both Fridays, the interbank rows of the two weeks, every Eurobond yield), and the mean of the stored P/E points over the AVERAGE formula's own window equals the workbook's P/E and dividend yield AVERAGE cells at 6 decimals. Two things in the workbook itself: two weekly turnover rows (weeks of 31 Aug 2017 and 31 Mar 2019) have two undated sum rows each with different numbers, so neither is imported; and the dividend yield series holds two 2008 values outside the form's 0.5 to 30 range, imported as they are.

## Weekly writes, dual running (checkpoint 3, `weekly.py`)

The tool writes the weekly figures to the store beside the files it already keeps. **The files stay the truth and no builder reads the store yet**; the store is filled so the history is there when the readers are switched over.

- **One path.** `weekly/analyst.py::_write` is the only function that writes `analyst.json` (save, carry and suggest all end in it). `_synced` wraps those three: it runs them under the file lock, then, with the lock released, calls `history.weekly.sync(week, before, after, db_path)` with the form as it was and as it is now. Only items that changed (a new value, or a change in whether the item still waits to be confirmed) are written. The routes pass `d.db_path`; tests pass a temp file or rely on conftest's per-test default.
- **What a form item becomes.** Fields: `pe`, `dividend_yield`, `turnover_ytd`, `foreign_ytd`, `placements`. Tables: `mmf` (subject = the fund as matched, dated the fund table's published date), `interbank` (rate by day), `eurobond_yields` (by issue and day), `foreign_history` (weekly net, dated its own week), `universe` (this Friday's price by company; last Friday's is last week's own point). The averages, targets, dates and typed text are not series. Values are the form's own cleaned text (a percentage as typed), exact decimals.
- **Origin and confirmation.** A saved item is `typed`, confirmed by "analyst (form)". A carried weekly item and a suggested running total are written as `carried` or `worked_out` with no confirmation, so `current()` does not return them; saving the item confirms it (a suggestion kept as it is stays `worked_out`, a changed number is `typed`, and the old point points at the new one). A slow-changing item used as carried is `carried` and confirmed.
- **Fetched figures.** `weekly/inputs.store` calls `record_upload` for a KCB weekly report (the coverage companies' prices) and a CBK bulletin (KESONIA by day) that is this week's: origin `fetched`, source "`<stored name> sha256 <hash>`", confirmed by "published source". They are written with `only_new`, so a figure the store already holds for that series and date (typed, confirmed or from an earlier upload) is never replaced, and uploading the same file twice adds nothing. A trial copy (`recheck.py`) passes `record=False`.
- **A failed store write never fails anything.** `sync` and `record_upload` catch every exception: the file was saved, the upload was kept. Each failure is one `log.warning` naming the series and date (at most six) and the exception's class, never a value (a PostgreSQL error can quote the row, so the driver's message is not logged; our own `HistoryError` text names only series and date), and adds one to `failed_writes()`. It is not a run event: a form save is not a run. Showing the count to the analyst is for the later `history.status` tool.
- **Statements.** `store.record_many` is batched: one series lookup, one query for the current points of the batch, one multi-row insert for the new points (a supersession takes three statements for its point). 300 points take under 15 statements (`test_a_batch_takes_a_handful_of_statements_not_one_per_point`), because a statement on Supabase is about 200 ms.
- **Not written yet:** the equities and fixed income series the readers take from other files (the NSE price list, the CBK auction results, the yield curve), the fund table and placements history, and the Digital Payments figures. Add each as its source is switched over.

## Reading the store behind a switch (checkpoint 4, `reads.py`, `replay.py`, `scripts/replay_history.py`)

`CYTONN_HISTORY_READS` (named in `.env.example` and `docker-compose.yml`; read from the process environment at each call, so `.env` counts once `load_env()` has run; an unknown value reads as `off` with one warning). **off** (the default): every reader is exactly what it was, and the store is not opened. **compare**: the form's figure is used; the store is read as well, each difference is logged by series and date (never a value; at most 20 lines a comparison, all counted) and counted in `reads.counts` (`compared`, `differences`, `failed_reads`). **on**: the store's figure, and the form's only where the store has no point for it. A store that cannot be read is a warning and a `failed_reads` count in both modes and the form's figure is used: a draft never fails on it. Only confirmed points are read.

The five readers, each a function of the week in `reads.py` and called from one place:

| Reader | Called from | Rule in the store |
| --- | --- | --- |
| The running totals' "before" (`eq.turnover.ytd`, `eq.foreign.ytd`) | `equities/weekly.running_total_suggestions` | The newest confirmed point dated in the previous week's report dates. Not older: a total from two weeks ago is not last week's. The sum of weekly points is not used; the replay reports it. |
| Foreign weeks and the streak (`eq.foreign.week`) | `Analyst.foreign_history` | Every confirmed weekly point before this week's Monday, oldest first. A point from a workbook import is a `Reading` (the workbook's history is complete), a point typed on the form is a `Typed`, so the builder's care with partial typed sums stays. |
| The total the year before closed on | `Analyst.field("foreign_prior_year")` | `equities_workbook.prior_year_total`, the workbook's own restart rule, run on the stored weekly and year-to-date points from 1 December of the year before. |
| Last Friday's price per company (`eq.price`) | `Analyst.universe` | The newest confirmed point dated in the previous week's report dates, read once for all companies (`last_prices`). A price typed by hand for last Friday stays in `on` (no form save writes last Friday's price). |
| The market P/E's historical average | `Analyst.field("pe_average")` | The mean of every confirmed `eq.pe` point from **12 Dec 2008** (`PE_AVERAGE_FROM`) to this week's, only when this week's point is there. The window is the workbook's AVERAGE range, read from its formulas in the 2 Oct, 30 Oct and 13 Nov 2026 workbooks: from the newest row down to the row dated 12 Dec 2008; the two 2008 dividend yield values and the earlier 2008 P/E rows are outside it. The dividend yield's average stays typed. |
| The fund table's previous week and the Top 5 comparison (`fi.mmf.rate`) | `Analyst.previous_mmf` (called by `money_market_blocks`) | The points of the latest day in the previous week the table was published on, best rate first. The store starts empty, so this works from the second week after dual running began. `cmmf_last_week` is still the form's. |

A store-backed cell says so in its source ("history store, ... (from the team's workbook, imported)" or typed on the weekly form) and, as every analyst input, is not auto-verified. `prose.typed` keeps a given second reading for a cell that is not a `Typed` (so the P/E average still carries the tool's own recomputation from an uploaded workbook, and a disagreement is still flagged).

**The replay** (`replay.run`, `scripts/replay_history.py`) forces `on`, takes a scratch SQLite file only, and compares the store with the equities workbook's own cells week by week, by the exact-match rule at the store's 8 places (6 for the P/E average, the builder's own): the "before" with last week's total; "before + the week's figure" with the week's total (a difference within 0.06 at two places passes, a larger one fails, and the one break per year beyond 1.0 is the new year's restart, a SKIP); the weeks before each week; the total the year before closed on; last Friday's price per company; the P/E average (the workbook states it once, for its latest week). The fund table has nothing to replay. Run on the 13 Nov equities workbook and the 14 Nov mastersheet imported into a scratch database (2026-11-18): 2280 PASS, 1 FAIL, 12 SKIP. The FAIL is the workbook's own: the turnover total on the row of the week ending 2 Jan 2026 is 0.84 off the sum of the row before and the week's figure (the foreign total that week is 0.06 off, within the drift). Ask the equities team which is right before switching to `on`.

## The "this week's rows" export (checkpoint 5, `rows_export.py`, `POST /api/export/weekly-rows/{week_ending}`)

A small separate .xlsx of the week's rows, from the store's **confirmed points only** (the form is never a second source), for an analyst to paste into the team's master workbooks. One sheet per master sheet that has weekly rows, named exactly as the readers name them (`eq.TURNOVER_SHEET`, `FOREIGN_SHEET`, `VALUATION_SHEET`, `UNIVERSE_SHEET`, `fi.LIQUIDITY_SHEET`, `EUROBOND_SHEET`, `MMF_SHEET`): Equities Turnover, Foreign Positions, NASI-PE & Dividend Yield, Universe of Coverage (the week's new "Price as at dd/mm/yyyy" column), Liquidity Indicators, Eurobond, Money Market Performance. Values only: the weekly sum and the running year-to-date on the two flow sheets are formulas in the master and are written as values, with a note; the AVERAGE row of the valuation sheet is not exported; percentages are fractions, as the masters hold them (`reads._number`).

- **Columns** are written left to right in the master's order, without the master's blank columns, and each sheet's notes say where each column sits in the master. Where the reader finds a column by label (the Universe's "Company" and its price columns, the fund table's Rank, Fund Manager and Effective Annual Rate) the letters and the company order and fund names come from the uploaded master; where the reader uses a fixed position (the turnover, foreign, valuation and liquidity sheets) the note gives the reader's constants. With no master uploaded for the section, the note says "No ... workbook is uploaded for this week: columns follow the reader's constants"; the Universe then lists the store's company keys alphabetically and the fund table names a fund by the store's key.
- **A missing point** is an empty cell and a note naming the series, the date and (for a company, a fund or a Eurobond issue) the key, never a value. An unconfirmed (carried or suggested) point is not exported.
- **The masters are only read** (`Workbook` holds the uploaded bytes read-only), and the file is written to `export_root` or `data/exports/weekly-rows/` and nowhere else (`Weekly rows, week ending <Friday>.xlsx`, replaced on each build). The route is 409 when an uploaded workbook cannot be read, 422 for a day that is not a Friday. No frontend button yet (checkpoint 6).
- It costs 13 reads of the store (`test_connection_counts.py`), nothing is written.
- Also found with checkpoint 5's route test: `running_total_suggestions` passed the form's field name (`turnover_ytd`) to `reads.running_before`, which needs the series key (`eq.turnover.ytd`), so `on` never found a point; it now maps through `history.weekly.FIELD_SERIES`, and `running_total_suggestions` takes the `db_path` the route has. With `off` nothing changed.

## The chat's view of the store (checkpoint 6, `agent/read_tools.py`, `reads.source_lines`, the export card's button)

- **`history_status`** (no arguments: this conversation's section and week): every series of the section (`CATALOG`'s section column), each `confirmed`, `unconfirmed` (only waiting points) or `none`, the counts and dates, how many subjects, and three plain numbers: `failed_store_writes` (`history.weekly.failed_writes()`), `failed_store_reads` and `compare_differences` (`reads.counts`), both since the process started. No value. A section with no series (Real Estate, Digital Payments, Focus) is refused.
- **`history_working(series, day)`**: the points of one series on one date of this week: origin, source kind, whether confirmed, the source reference and, for a figure the tool worked out, its working (the suggestion's own note, written by code, shown up to 400 characters: `tools.LONG`, every other string is still cut at 120). **The market P/E, the fund table and the placements (`reads.CONFIDENTIAL`) give their provenance only**: no value, subject or working, and no source reference when it is the working. This is enforced in the tool, not only in its shape. Other series show their stored value and subject. A date outside Monday to Friday of the conversation's week, an unknown series or an extra argument is refused.
- **`week_status`** adds a `source` line to an entry of `carried_or_suggested` when the store holds that field's unconfirmed point for the week ("suggested: last confirmed total for 25 Sep plus this week's figure", "carried: from the week ending 2026-09-25", built from the point's origin and a date in its reference, never from its note). `readiness.classify` is still pure and unchanged; the lines are added in the tool, from `reads.source_lines`, which is empty with `CYTONN_HISTORY_READS` off (so the output is exactly what it was) and on any store error. Groups and counts are never changed. The readiness card the API posts and re-reads comes from the same tool, so it carries the line too.
- **The button** "This week's rows (xlsx)" is on the chat's export card (`ExportBar` with `rows`; `lib/rows.ts`): it calls `POST /api/export/weekly-rows/{week_ending}`, saves the file the way the Word export is saved, and shows the 422 and 409 answers in plain words under the card. It is off for a period that is not "Week ending YYYY-MM-DD". The hidden overview's export bar has no such button.

## Fetched points (Phase 5)

`history.weekly.record_fetch` writes a fetched table's points once per series and date (`only_new`, origin `fetched`, source kind `source`, `source_ref` = the fetch note with the sha256, confirmed by `store.FETCHED`); `sync` skips a table still marked fetched, so the form save writes nothing twice. Interbank goes to `fi.interbank.rate` (4 dp from KESONIA; `fi.kesonia` stays the bulletin's 2 dp). New series `fi.remittances.total` and `fi.remittances.north_america` (usd_mn, month cadence, `as_of` the month's last day); typed remittances now sync to them too (`TABLE_SERIES`). The store this machine reads held no `fi.interbank.rate` points on 2026-11-18, so the overlap with the workbook history could not be counted.
Fetched Eurobond openings write `fi.eurobond.yield` per issue and day, with both bulletins' addresses and sha256 in the source reference.
